## 0. 本文的写法说明

要回答这两个问题，必须先建立一个**统一的时间坐标系**（第 1 节），再推出一个**相位漂移公式**（第 2 节）。
这两个东西一旦立住，第 3、4 节的大部分结论都是它的直接推论——包括"延迟超过半拍到底行不行"这个问题的精确答案（结论：**行，而且延迟的秘密不在"拍"上，在"步"上**）。

文中符号统一如下：

| 符号 | 含义 | 单位 |
|---|---|---|
| `C` | 用户步频（cadence） | 步/分 |
| `B` | 歌曲 BPM | 拍/分 |
| `m` | 当前播放倍速（multiplier） | 倍 |
| `m*` | **匹配倍速** = `C / B` | 倍 |
| `P` | 歌曲拍周期 = `60 / B` | 歌曲秒 |
| `T` | 脚步周期 = `60 / C` | 墙钟秒 |
| `off` | `tempo::beatOffset()` 的返回值 ∈ [-1, 1] | offset 单位 |

**一条恒等式贯穿全文：**

```
T = P / m*          （脚步周期 == 拍周期 ÷ 匹配倍速）
```

## 0.5 零数学版：先看一遍全部机制

> **只看这一节也能懂全篇。** 后面所有公式都只是这里的精确化，一个积分符号都不用看。

### 0.5.1 一个类比解决一半问题：两个转盘

把**音乐的节拍**想成一个转盘上的指针：每来一拍，指针转一圈。
把**你的脚步**想成另一个转盘上的指针：每迈一步，指针转一圈。

```
        音乐转盘                    脚步转盘
          ╭───╮                      ╭───╮
        ╱   ↑   ╲                  ╱   ↑   ╲
       │    │    │                │    │    │
        ╲   │   ╱                  ╲   │   ╱
          ╰───╯                      ╰───╯
       一拍转一圈                    一步转一圈
```

**两根指针之间的夹角，就是代码里的 `off`（相位差）。**
夹角用「半圈」当单位量，所以范围是 −1 ~ +1：

| `off` | 大白话 | 听感 |
|---|---|---|
| `0` | 两根指针完全重合 | **拍点正踩在脚上**（最好） |
| `+1` | 错开半圈 | **拍点正好落在两步中间**（最坏） |
| `−1` | 从另一边错开半圈 | 和 `+1` 是**同一个物理状态**（这就是「圆」的由来） |

**这一条顺带解释了三件事：**

1. 为什么 `off` 是 [−1, +1] 而不是 [0, 1] —— 它量的是**夹角**，左右对称；
2. 为什么 `+1` 和 `−1` 是一回事 —— 转半圈，从哪边转过去都一样；
3. 为什么下面会出现「混叠」 —— **夹角是个圈，绕满一圈就回到原点。**

### 0.5.2 为什么「匹配倍速」之后，夹角就冻住了

两个转盘**转速相同**时，两根指针的相对夹角**永远不变**（一起转，谁也没追上谁）。

`TempoFollower` 干的事，就是让音乐转盘的转速 = 你脚步转盘的转速。这个转速叫**匹配倍速**：

```
匹配倍速 m* = 你的步频 ÷ 歌曲 BPM
例：步频 180 步/分，歌曲 120 BPM  →  m* = 180/120 = 1.5 倍速
```

**只要倍速停在 1.5，夹角就冻住了 —— 这就是 HOLD（保持）状态存在的全部意义。**
（代码注释里那句「相位在步频匹配时静止」，说的就是这个。）

### 0.5.3 夹角什么时候会「跑开」？—— 漂移

倍速差一点点，两个转盘就会慢慢拉开。这就是**漂移**。

```
每走一步，夹角大约变化 = 2 × 倍速的相对误差
```

那个 `2` 是「用半个拍当单位」带来的，不用管它。看实数（180 步/分，一步 1/3 秒）：

| 倍速差 | 每步夹角变化 | 多少步跑出「好」窗口 | 大约几秒 |
|---|---|---|---|
| 0% | 0 | 永远不会 | ∞ |
| 1% | 0.02 | 25 步 | 8 秒 |
| 2% | 0.04 | 12 步 | 4 秒 |
| 5% | 0.10 | 5 步 | 1.7 秒 |

**⇒ 精度要求非常苛刻：差 1% 就是 8 秒跑偏，差 5% 不到 2 秒就跑偏。**
所以跟随器必须一直盯着、随时微调 —— 这就是 ADJUST / CHASE / HOLD 三个状态存在的理由。

### 0.5.4 ★ 延迟的秘密：**按「步」算，不按「秒」算**

这是全文最反直觉、也最重要的一条。

因为夹角是个圈（0.5.1），**延迟绕满一圈就看不出来了**：

```
延迟 0 秒      →  夹角偏 0        →  完美
延迟 半步      →  夹角偏半圈      →  最坏（拍点落在两步中间）
延迟 一整步    →  夹角偏一整圈    →  完美（和没延迟一样！）
延迟 一步半    →  夹角偏半圈      →  最坏
```

**⇒ 一句话：只有「延迟 ÷ 一步的时间」的余数才看得见，而且最坏只错半拍。**
打个比方：**手表拨快 12 小时，你看表还是准的。**

再给张实数表（180 步/分，一步 333 毫秒）：

| 端到端延迟 | 相当于 | 听感 |
|---|---|---|
| 40 ms | 偏 0.24 | 刚出「完美」窗口，基本听不出 |
| 83 ms | 偏 0.50 | 偏 1/4 拍，开始「有点飘」 |
| **167 ms** | **偏 1.00** | **偏半拍（最坏）** |
| 250 ms | 偏 −0.50 | 又变好了（反方向偏 1/4 拍） |
| **333 ms** | **偏 0.00** | **完美 —— 整整一步的延迟等于没有延迟** |

**⇒ 所以「延迟超过半拍还能不能工作」——能，而且很稳。超过半拍的部分对系统根本不可见。**
真正要收拾的是另外两件事：

1. **延迟的抖动**（不是延迟本身）：抖动要小于 17~25 毫秒，否则「完美」窗口框不住脚步；
2. **半拍以内的那点残余**：靠一次标定把它折回 0。

### 0.5.5 三种模式，一句话区别

| 模式 | 谁决定播放速度 | 夹角会漂吗 |
|---|---|---|
| **步频跟随** | 你**实测**的步频 | **会漂**（步频是实时变的），所以要一直追 |
| **恒定 BPM** | 规定的一个数字（比如 170） | **不漂** |
| **曲线** | 你画的曲线 | **不漂**（曲线怎么变都不漂） |

**为什么后两种不漂？** 因为它们算倍速用的是同一个数字：

```
倍速 = 规定步频 ÷ 歌曲 BPM
```

既然「规定的步频」和「算倍速用的步频」是同一个数，**两个转盘就永远同步** ——
夹角一开始是多少，就永远是多少。（这就是 §8.1 那个「定理」的全部内容。）

**⇒ 所以开环模式下只有一个问题要回答：一开始夹角是多少？**

### 0.5.6 切歌 / 接歌，一句话本质

**切歌 = 把 B 的转盘接到 A 的转盘上，让两根指针重合。**

因为两首歌在墙钟上的转速**是一样的**（都是「一步一转」，来自 §4.2），
所以只需要在**切换的那一瞬间**让指针对上，之后永远对上。

由此得到一条极好用的规则：

> **把 B 的入点前后移动整数个拍，相位完全不变。**

因为移整数拍 = 移整数步 = 转盘整整转了整数圈。
**⇒「从哪里进」和「对不对得齐」是两个独立的问题** —— 可以先挑好听的入点，再管对齐。

### 0.5.7 名词对照表

| 术语 / 符号 | 一句话大白话 |
|---|---|

| 歌曲时间 `songSec` | 进度条上的时间（1.25 倍速播 10 秒，进度条走 12.5 秒） |

## 1. 公共地基：三条时间轴，以及 offset 的"周期是一拍"

### 1.1 三条轴

代码里实际存在三条互不相同的时间轴，混用是这类系统 90% 的 bug 来源：

| 轴 | 谁在推进 | 用途 |
|---|---|---|
| **墙钟轴 wallSec** | 单调时钟（`steady_clock`） | 传感器时间戳、脚步间隔、`TempoFollower::advance` 的 dt |
| **歌曲原速轴 songSec** | `∑ m · Δwall`，即 = `getInputPosition() / sampleRate` | `beatOffset` 的输入、`CppDataAnalyzer` 的段落查询 |
| **输出帧轴** | 声卡消费速度 | 用户**实际听到**的那一刻 |

`songSec` 是我们唯一能直接读到的"音乐进度"，它按 `m` 倍速度走：**1.25 倍速播 10 墙钟秒 ⇒ songSec 前进 12.5 秒**。这一点 `TempoFollower.hpp` 的文件头已经写明了，是整个设计的正确基础。

第三条轴（输出帧轴）当前代码里**完全不存在**——这是第 3 节要重点处理的漏洞。

### 1.2 offset 的几何形状

`beatOffset(songSec, B, firstBeat)` 的实现是：把 `songSec` 对拍周期 `P` 取模，落在 [0, P/2) 就映射到 [0, +1)，落在 [P/2, P) 就映射到 [-1, 0)。

所以：

- `off = 0` ：正中拍点
- `off = +1`：**晚半拍**
- `off = -1`：**早半拍**
- **周期是 1 拍 = 2 个 offset 单位**，offset 是一个**圆**，不是直线。

这个"圆"的性质是后面一切"混叠"结论的来源。

### 1.3 一个 offset 单位等于多少墙钟秒？（重要）

> **💡 大白话**
> `off` 用「半个拍」当单位，那半个拍是多少**秒表秒**？
> 一拍 = `60/B` 歌曲秒，而歌曲秒要乘上倍速才是你的秒表秒，
> 所以 **1 个 `off` 单位 = 半个拍 ÷ 倍速 = `30/C` 秒表秒**。
> **结论：它只跟步频有关，跟你放哪首歌完全无关。**
> 180 步/分时就是 1/6 秒 —— 记住这个数，「偏 1 个单位」就是「偏 1/6 秒」。

offset 的刻度是"半拍 ÷ 歌曲秒"，而歌曲秒要走 `m*` 倍才是墙钟秒：

```
1 offset 单位 = (P/2) 歌曲秒 = (P/2) / m* 墙钟秒
             = (30/B) / (C/B)
             = 30 / C   墙钟秒
```

**所以：1 个 offset 单位 = 30/C 墙钟秒。它只跟步频有关，跟歌曲无关。**

| 步频 C | 1 offset 单位 | 半拍（=±1 单位） |
|---|---|---|
| 150 步/分 | 200 ms | 200 ms |
| 180 步/分 | 167 ms | 167 ms |
| 200 步/分 | 150 ms | 150 ms |

而 `T = 60/C`，所以 **±1 个 offset 单位 = ±T/2 = 半步**。

> ⚠️ **注意这里有一个定义冲突需要钉死。**
> `TempoFollower::delayOffset()` 当前的换算是 `stepDelaySec * songBPM_ / 30.0`。
> 但根据上面的推导，墙钟延迟 τ 正确地换算成 offset 应该是
> ```
> dOff = τ · C / 30 = τ · (B · m*) / 30 = τ · m* · B / 30
> ```
> 也就是**差了 m\* 倍**（真实场景 m\* ∈ [0.7, 2.0]，最多差一倍）。
> 换句话说：当前代码里的 `stepDelaySec` 语义上其实是"**歌曲秒**延迟"，而文档注释写的是"秒（计步检测偏晚）"。
> 这不是要现在改，但**接线时必须先决定钉死哪一种**，否则延迟补偿会系统性偏掉。
> 建议：把上层对外的参数定义成**墙钟秒**，在写入 `stepDelaySec` 前除以 `m*`；或者干脆把上层参数直接定义成 **offset 单位**（见 3.8，我更推荐后者）。

## 2. 相位动力学：一个公式解决大半问题

### 2.1 相位漂移公式

> **💡 大白话**
> 就是 §0.5.3 那张表：**两个转盘转速差多少，每走一步夹角就多错开多少。**
> `Δoffset/步 = 2 × (m/m* − 1)` 里的那个 `2`，只是「用半个拍当单位」带来的系数，不用记。
> **要记的是结论**：倍速差 1% → 每步错开 0.02 → 25 步（8 秒）后错开整整半个拍。

当倍速 `m` 偏离匹配倍速 `m*` 时，拍点与脚步之间的相位会持续漂移。推导：

```
拍点速率（拍/墙钟秒）   = m / P
脚步速率（步/墙钟秒）   = 1 / T = m* / P
相位积累速率（拍/秒）   = (m − m*) / P
换算成 offset 单位（×2）：2(m − m*) / P
除以脚步速率（×T）：     2(m − m*) / P · (P/m*) = 2(m/m* − 1)
```

```
┌──────────────────────────────────────────────┐
│  Δoffset / 每个脚步 = 2 · (m / m* − 1)        │
└──────────────────────────────────────────────┘
```

**这一个公式解释了整个状态机的存在理由：**

| 倍速相对误差 | 每步相位漂移 | 走出 perfect(±0.25) | 走出 good(±0.5) | 绕一圈(2单位) |
|---|---|---|---|---|
| 0 %（完美匹配） | 0 | 永不 | 永不 | 永不 |
| 1 % | 0.02 | 12 步 | 25 步 | 100 步 |
| 2 % | 0.04 | 6 步 | 12 步 | 50 步 |
| 5 % | 0.10 | 2.5 步 | 5 步 | 20 步 |

（180 步/分时，25 步 ≈ 8.3 秒）

### 2.2 直接推论

1. **HOLD 之所以"相位静止"，是因为 HOLD 输出 `stableTarget_`，而稳定后 `stableTarget_ ≈ m*` ⇒ 漂移率 → 0。** 这是 HOLD 存在的全部意义，代码注释里说的"相位在步频匹配时静止"就是这个公式的 ε=0 情形。

2. **精度要求非常苛刻。** 要让相位在 10 秒内不漂出 good 窗（±0.5），需要 `2ε · (C/60) · 10 < 0.5` ⇒ `ε < 1.5/C`。180 步/分时 ε < 0.83%。这就是为什么 `holdBasisReady()` 要用 `convEps = 2%` 把关——2% 在数学上其实已经偏松，实际能稳住是因为稳态下 `stableTarget_` 收敛得远比 2% 紧。

3. **`chaseMax = 5%` 的权限是够的。** 追逐以最大 0.1 单位/步 的速度搬动相位，搬 1 个单位（半拍）需要 10 步 ≈ 3.3 秒。所以任何相位失配都能在几秒内拉回来——**前提是失配是"真失配"，而不是"恒定偏置"**（见第 3 节）。

## 3. 问题二：TempoFollower × StepDetector × LiveStretchPlayer

> **💡 大白话版问题**
> 计步器识别你落脚，有几十毫秒延迟；蓝牙耳机把音乐送进你耳朵，又有上百毫秒延迟。
> 两者加起来可能**超过半拍**（180 步/分时，半拍只有 167 毫秒）。
> **问：延迟这么大，跟随器还能把音乐和脚步对上吗？**
> **答：能，而且很稳。** 原因很反直觉 —— **超过半拍的延迟对系统根本不可见**（§0.5.4）。
> 真正要动手的是另外两件事：压掉延迟的**抖动**，标定掉**半拍以内的残余**。

### 3.1 目标数据流

```
[ArkTS / OH_Sensor]  加速度计，标称 50 Hz
        │  ax, ay, az, t_sensor
        ▼
[NAPI 批量入口]  onSensorBatch(Float32Array, Uint32Array/时间戳)
        │
        ▼
   steplib::StepDetector::update(ax, ay, az, t)
        │  同步回调（就在 update() 内部触发）
        ▼
   StepEvent {
        timestamp            ← ★ 波峰时刻，已被检测器「回填」，不是上报时刻
        detection_latency_s  ← 上报时刻 − timestamp
        cadence_spm, index, confidence, ...
   }
        │
        │  ① 用 timestamp 反查当时刻的 songSec（见 3.3）
        ▼
   tempo::TempoFollower::addFootstep(wallSec = e.timestamp, songSec)
        │
        │  ② 50 Hz 传感器批次末尾补一次 update(now)
        ▼
   TempoFollower::currentMultiplier()
        │
        ▼
   LiveStretchPlayer::setSpeed(m)   ← 线程安全，直接生效
```

**结论先行：这条链不需要独立的控制线程。** `TempoFollower::update()` 只做两件事——推进 `base_` 的指数平滑、复查状态退出条件；而 `refreshRates()` 在没有新脚步时是空操作。所以只要在每批传感器处理末尾调一次 `update(steady_now())` 就足够了。这也顺带绕开了"两个线程同时调 `advance()` 导致 `lastWall_` 打架"的问题。

### 3.2 延迟分解：一共有四种，必须以不同方式对待

| # | 延迟来源 | 量级 | 性质 | 处理方式 |
|---|---|---|---|---|
| ① | **检测算法延迟**（等信号回落确认波峰 + 滤波器群延迟） | 0～60 ms（实测最坏 60 ms） | 抖动 | **检测器已经回填了 timestamp，等于自动补偿** |
| ② | **生物力学相位**（合加速度波峰 ≠ 脚触地时刻；波峰通常出现在支撑期中段） | 50～200 ms | 近似恒定，但随配速/穿鞋/佩戴位置缓变 | 标定值 → `stepDelaySec` |
| ③ | **音频输出延迟**（环形缓冲 + OH_AudioRenderer 缓冲 + DAC + **蓝牙耳机 100～300 ms**） | 20 ms（有线）～300 ms（蓝牙） | 恒定（同一副耳机） | **当前代码完全没建模**，必须进 `stepDelaySec` |
| ④ | **宿主回填时的样点配对误差** | 取决于实现 | 抖动 | 用 3.3 的公式消除 |

**核心判断：①②③ 都是"同一个测量路径上的恒定时间偏置"，只能也必须合成一个数字来标定；④ 是纯实现问题，做对了就是 0。**

注意 ② 和 ③ 的**符号相反**（推导见 3.8）：
- 检测/生物力学偏晚 ⇒ 需要把拍点也往后推 ⇒ 正
- 输出偏晚 ⇒ 用户听到的拍点比代码以为的晚 ⇒ 需要把拍点往**前**推 ⇒ 负

**所以蓝牙耳机（+250 ms）和"检测偏晚"（+100 ms）会互相抵消一部分。这就是为什么必须端到端标定，不能分项相加。**

### 3.3 ★ 关键实现点：StepEvent.timestamp 是"回填的"

`step_detector.hpp` 第 174 行写得很清楚：

```cpp
double timestamp = 0.0;            // 加速度波峰的时刻 == 落脚时刻（秒）
double detection_latency_s = 0.0;  // update() 被调用的时刻 − timestamp（秒）
```

**检测器吐出来的是"事情真正发生的时刻"，不是"它被吐出来的时刻"。** 这是一个非常正确的设计，但宿主很容易把它浪费掉——如果宿主在上报的瞬间去读 `getInputPosition()`，就等于把 ① 又加回去了。

正确做法（二选一）：

**A. 用速度反推（推荐，简单）**

```
songSec_at_step = songSec_now − m_now × (now − e.timestamp)
```

其中 `songSec_now = player.getInputPosition() / sampleRate`，`m_now = follower.currentMultiplier()`。
回看窗口只有几十毫秒，用当前倍速线性反推的误差在亚毫秒级。

**B. 维护一个 (wall, songSec) 环形历史，按 wall 插值**

更精确，但要自己管一个 50 Hz 的历史环（约 0.5 秒 = 25 个点就够）。

**为什么这一步不能省：** 见 3.7。

### 3.4 延迟对闭环稳定性的真实影响——**几乎没有**

> **💡 大白话**
> 直觉会说「延迟 200 ms，闭环肯定要振荡」。但这个环**每迈一步才看一次数据**（一步 333 ms），
> 而它要调整的东西（两个转盘的夹角）变化得**非常慢**（秒级）。
> 一句话：**关节比节拍慢得多，一点点延迟根本不算事。**
> 实数：测量延迟 0.5 秒以内完全无感；0.5~1.5 秒只是收敛慢一点，也不会振荡。

这是最容易被直觉误导的地方。直觉会说"延迟 200 ms，闭环肯定要振荡"，但实际不是，原因是**这个闭环的采样周期本来就是"一步"**：

```
被控对象：相位 = ∫ 2(m/m* − 1) · (C/60) dt      ← 一个积分器
反馈量：  只有落脚那一刻才能观测到相位
控制器：  P 控制，输出被 chaseDelta(1%/步) 限速、被 chaseMax(5%) 限幅
```

把公式 2.1 离散化，取 `chaseCorr = −chaseMax · offset`（未触及限速时）：

```
off[n+1] = off[n] − 2·chaseMax·off[n]·(1/1) ... 整理后 ≈ (1 − 0.1)·off[n]
```

即闭环时间常数 ≈ 10 步 ≈ **3.3 秒**（180 步/分）。而环内延迟 = 1 个脚步周期（333 ms）+ 测量延迟。
**即使测量延迟加到 300 ms，环内总延迟也只有 633 ms，是闭环时间常数的 1/5——相位裕度依然巨大。**

粗略结论：
- 测量延迟 **< 0.5 秒**：对稳定性完全无感。
- **0.5 ~ 1.5 秒**：开始影响收敛速度，但不会振荡（因为还有 `chaseDelta` 限速和 `offsetEMA` 一阶滤波双重阻尼）。
- **> 2 秒**：才需要考虑给控制器降增益。

**所以"延迟太大导致跟随器失效"这个担心，在稳定性维度上是不成立的。**

### 3.5 延迟对"锁在哪"的影响

同样先给结论：**恒定延迟不会阻止系统进入 HOLD。**

控制器优化的是 `err = |off_meas − delayOffset()|`，它会把**测得的**偏移压到 0。恒定延迟只是让 `off_meas = off_true + b`（b 为延迟带来的偏置），控制器把 `off_meas` 压到 0，也就是把 `off_true` 停在 `−b` 处。整个过程中 `hitRate` 会照样爬到 1、`hitStreak` 会照样攒够、HOLD 会照样进入。

**唯一变化的，是"听到的拍点落在脚步的哪儿"。**

### 3.6 ★ 混叠定理：任何恒定延迟，感知误差都不会超过半拍

> **💡 大白话**
> 就是 §0.5.4 那条：**手表拨快 12 小时，你看表还是准的。**
> 夹角是个圈，延迟绕满一圈就看不出来了 ——
> **只有「延迟 ÷ 一步的时间」的余数才可见，而且最坏只错半拍。**
> 所以延迟多大都不可怕，可怕的是**它不稳定（抖动）**。

因为 offset 是一个周长 2 的圆（1.2 节），恒定偏置 b 与 `b − 2k` 在系统看来**完全等价**。而 `2 个 offset 单位 = 1 拍 = T 墙钟秒`，所以：

```
┌────────────────────────────────────────────────────────────┐
│  延迟的秘密不在「拍」上，在「步」上：                       │
│  只有 τ 对 T（脚步周期）取模之后的部分才是可见的。           │
│  等效 offset 偏置 = (τ mod T) · C / 30，再折到 [-1, +1]。   │
└────────────────────────────────────────────────────────────┘
```

**取 C = 180 步/分（T = 333 ms，1 单位 = 167 ms）：**

| 端到端延迟 τ | τ mod T | 等效 offset | 相当于 | 用户感受 |
|---|---|---|---|---|
| 0 ms | 0 | 0.00 | 0 | 完美踩点 |
| 40 ms | 40 | +0.24 | 晚 0.12 拍 | 刚出 perfect 窗，肉耳几乎无感 |
| 83 ms | 83 | +0.50 | 晚 1/4 拍 | good 窗边缘，开始"有点飘" |
| **167 ms** | 167 | **+1.00** | **晚 半拍** | **拍点落在两步正中间（最坏）** |
| 250 ms | 250 | −0.50 | 早 1/4 拍 | 又变好了 |
| **333 ms** | **0** | **0.00** | 0 | **完美——整整一个脚步周期的延迟是不可见的** |
| 500 ms | 167 | +1.00 | 半拍 | 又回到最坏 |

```
┌──────────────────────────────────────────────────────────────┐
│  ⇒ 未补偿时，感知误差的最坏值恒为 ±1 单位 = ±半拍，永不更大。 │
│  ⇒ 配合 delayOffset()（限幅 ±(1−hitWin)=±0.75）后，           │
│     最优残差 ≤ 0.25 单位 = 1/8 拍。                           │
└──────────────────────────────────────────────────────────────┘
```

**这个系统是"失效安全"的：延迟再离谱，也只是错半拍，不会错一拍、不会抖、不会失控。**

### 3.7 ★ 真正会坏的是**抖动**，不是**延迟**

> **💡 大白话**
> 延迟 =「每次都晚 0.2 秒」→ 好办，整体往后挪 0.2 秒就行（标定）。
> 抖动 =「有时晚 0.1 秒、有时晚 0.3 秒」→ 没法标定，只能靠滤波和迟滞去吸收。
> **实数门槛**：抖动要小于 17~25 毫秒（约 `3/B` 秒），否则「完美」窗口框不住脚步。
> 这正是必须用检测器**回填的时间戳**（§3.3）的原因 —— 它能把最大的那部分抖动直接消掉。

延迟是恒定偏置 → 可以标定。
延迟**抖动** → 变成相位测量噪声 → 不可标定，只能被滤波和迟滞吸收。

给出量化边界。相位噪声 σ（单位：offset）与延迟抖动 σ_τ 的关系：`σ = σ_τ · C / 30`。
HOLD 期间要求脚步稳定落在 perfect 窗（±0.25）内，经验上噪声要控制在窗宽的 40% 以内：

```
σ_τ · C / 30 < 0.1   ⇒   σ_τ < 3 / B  秒
```

| 歌曲 BPM | 允许的延迟抖动 σ_τ |
|---|---|
| 120 | 25 ms |
| 150 | 20 ms |
| 180 | 17 ms |

**17～25 ms 是很紧的。** 而 ① 检测算法延迟的抖动（等信号回落 `turn_down_ratio·σ` 才确认波峰，回落快慢取决于信号形状/幅度/步频）完全可能落在几十毫秒量级。

**⇒ 这就是 3.3 那个"必须用 `e.timestamp` 反查 songSec"的量化理由。用回填时刻，① 的抖动被彻底消掉，只剩 ③（同一副耳机内抖动很小）和 ②（缓变）。不用回填时刻，抖动直接吃掉 HOLD。**

**同时这也解释了 `hitWin / goodWin` 双窗口迟滞的真实用途**：`hitWin = 0.25` 是"进 HOLD 难"（要求干净），`goodWin = 0.50` 是"出 HOLD 难"（容忍噪声）。这不是为了好看，正是为了吸收相位测量噪声——**0.25 → 0.50 这 2 倍的信噪比余量，恰好覆盖了 3.6 里"未补偿恒定偏置最坏半拍"的区间。**

### 3.8 delayOffset 的标定：符号与流程

> **💡 大白话**
> 只有两个延迟要管，**而且方向相反**：
> - **计步延迟**（脚落地了，算法过一会儿才报告）→ 要让拍点也**晚一点** → 符号 **正**
> - **输出延迟**（代码产出了，耳机过一会儿才响）→ 要让拍点**早一点** → 符号 **负**
> **所以蓝牙耳机（+250 ms）和检测偏晚（+100 ms）会互相抵消一部分。**
> **⇒ 必须端到端量一个数，不能分项相加。**

**符号推导（务必按这个符号来）：**

设真实脚步发生在 offset 为 `off_true` 的位置，我们想让用户听到的拍点正好踩上它。

1. **检测/生物力学偏晚 τ_s（墙钟秒）**
   上报时刻的 songSec 比真值晚 `m*·τ_s`，
   `off_meas = off_true + m*·τ_s·B/30`
   要让 `off_true = 0`，需要目标 `off_meas = +m*·τ_s·B/30`
   ⇒ **符号为正，量值 = τ_s·C/30**

2. **输出延迟 L_out（墙钟秒）**
   用户听到的拍点 = 代码产出拍点 + L_out。要让"听到的拍点"踩上脚步，代码产出的拍点必须**提前** L_out。
   `off_true' = −m*·L_out·B/30`
   ⇒ **符号为负，量值 = −L_out·C/30**

**合计（都用 offset 单位）：**

```
dOff_total = (τ_s − L_out) · C / 30        ← 墙钟秒
dOff_total = τ_s·C/30 − L_out·C/30
```

**标定流程（建议按这个顺序做，前面几步都是可复现的客观测量）：**

| 步骤 | 做什么 | 怎么测 |
|---|---|---|
| 1 | 保证 ① 已由回填时间戳消除 | 代码审查：`addFootstep` 的第一个参数必须是 `e.timestamp` |
| 2 | 测 `L_out` | 编码一段位置标记（例如扫频），测"写入位置 → 实际可听位置"的帧差；蓝牙耳机再叠加厂商标称延迟 |
| 3 | 估算 `τ_s`（生物力学） | 同步录一段"加速度 + 脚步落地声"，做互相关，量出波峰相对落地的偏移 |
| 4 | 合成 `dOff_total`，折到 [−1, 1]，再折到 [−0.75, 0.75] | `dOff = dOff − 2·round(dOff/2)` |
| 5 | 用户终校 | UI 给一个"对齐微调"滑条，**单位直接就是 offset × 100**（−50 ~ +50），拖到"踩点最舒服" |

第 5 步不能省：**"对齐"最终是主观量**——有人喜欢音乐**压**在脚上（领先 5~10 ms 更有推动感），有人喜欢**跟**在脚后。给用户一个 ±1/8 拍的微调，比任何自动标定都管用，而且成本极低。

> 注：因为"恒定偏置"是对称的感知量，用户微调出来的那个值，本身就已经把 ②③ 一起吸收了——**所以第 5 步其实可以只做第 5 步**。前 4 步的价值在于给出一个靠谱的默认值，让用户不需要每次都调。

### 3.9 接线契约（必须遵守的 5 条）

```
① wallSec 必须是 e.timestamp（回填时刻），并且和 songSec 用同一个时钟源。
   推荐：在 NAPI 边界统一用 C++ steady_clock，传感器批次到达时记 now，
   批次内第 i 个样点的时间 = now − (n−1−i)·(1/rate)。

② songSec 必须用 3.3 的公式反查，不能直接读「现在」的位置。

③ 顺序：先在回调里 addFootstep(e.timestamp, songSec_at_step)，
   再在整批处理完后 update(steady_now())。不要从两个线程分别调
   addFootstep 和 update（lastWall_ 会被来回拉扯）。

④ stepDelaySec 的语义（墙钟秒 / 歌曲秒 / offset 单位）必须在写入侧统一，
   参考 1.3 的警告。

⑤ 传感器停摆不需要 reset：TempoFollower 的 maxDtSec(0.5) 会夹住时间跳变，
   wallBuf_ 的中位数滤波会自动丢掉因停摆产生的巨大间隔。
```

### 3.10 对"延迟超过半拍还能不能生效"的**分层回答**

| 层次 | 结论 | 依据 |
|---|---|---|
| **稳定性**（会不会振荡/发散） | **完全不受影响**，延迟 < 0.5 s 无感，< 1.5 s 也稳 | 3.4：闭环采样周期本来就是"一步"，被控对象时间常数是秒级 |
| **能否进入 HOLD** | **不受影响**，恒定延迟照样进 HOLD | 3.5：控制器压的是"测得偏移"，偏置对它不可见 |
| **感知对齐**（用户听感） | **最坏错半拍，永不更差**；配合 delayOffset 后 ≤ 1/8 拍 | 3.6 混叠定理 |
| **HOLD 的保持** | **这才是会坏的地方**，但坏在"抖动"不在"延迟" | 3.7：要求 σ_τ < 3/B ≈ 17~25 ms |

**所以：是的，"延迟大过半拍"完全能正常生效——因为超过半拍的部分对系统根本不可见。真正需要花力气的是把延迟的抖动压掉（用回填时间戳），以及用一次标定把"半拍以内那部分"折回 0。**

## 4. 问题一：切歌对拍

> **💡 大白话版问题**
> 歌 A 放到一半要换成歌 B，用户正按某个步频在跑。**不能让音乐在换歌那一瞬间「跳」一下。**
> 要保证两件事：换歌前后**快慢不变**（速度对齐）、**拍点落在同一个位置**（相位对齐）。
> **好消息**：只要两首歌都用「你的步频 ÷ 它的 BPM」这个倍速，**快慢自动就是一样的**，不用额外处理（§4.2）。
> 所以真正要做的只有**相位**一件事，而且**只需要在切换的那一瞬间做一次**，之后永远对齐。

### 4.1 目标的形式化

设切歌发生在墙钟时刻 `t_sw`。A 歌正在按 `m_A` 播放，B 歌准备接入。

要求：**B 的拍点网格，在墙钟上与 A 的拍点网格重合**（速度 + 相位）。

为什么对齐"网格"而不是对齐"脚步时刻"？见 4.11——这是个很关键的选择。

### 4.2 ★ 速度侧是**自动**对齐的（一个让人安心的结论）

`TempoFollower` 让每首歌的 `m = C / B`，于是：

```
A 歌的拍点速率（拍/墙钟秒） = m_A / P_A = (C/B_A) / (60/B_A) = C / 60
B 歌的拍点速率（拍/墙钟秒） = m_B / P_B = (C/B_B) / (60/B_B) = C / 60
```

**两首歌的拍点速率都恒等于 `C/60`——也就是脚步速率。** 只要：
- 两首歌的 BPM 都正确；
- 两首歌都在用**同一个** cadence 估计（同一个 `TempoFollower` 实例）；
- 倍速在切歌瞬间**没有经过斜坡**；

那么**速度侧根本不需要额外对齐逻辑**。

**⇒ 唯一的坑是斜坡。** `setSong()` 只改 `target_`，不动平滑锚点 `base_`；在 `tau = 2.0` 的指数逼近下，切歌后会有 2 秒左右"新歌以错误的速率播放"的过渡。2 秒 × 3 拍/秒 ≈ **6 拍**的相位误差累积，这是听得出来的撕裂。

**⇒ 必须用 `setMultiplier()` 做瞬时快照**（它把 `mult_` 和 `base_` 一起设过去，并回到 ADJUST）。代码里已经有这个接口，注释也明说了这个用途。

### 4.3 相位侧的唯一自由度和它的性质

B 歌可以在**任意位置**开始播（`seekTo`），而且拍的相位只取决于"从哪个位置开始"和"什么时候开始"。

B 歌的第 j 拍位于歌曲位置 `f_B + j·P_B`。若从 `s_B` 开始、在墙钟 `t_start` 起播，则该拍在墙钟上出现的时刻是：

```
t_beat(j) = t_start + (f_B + j·P_B − s_B) / m_B
```

### 4.4 ★ 整拍不变性（一条极好用的推论）

> **💡 大白话**：移整数拍 = 移整数步 = 转盘整整转整数圈，指针位置当然不变（§0.5.6）。
> **⇒「从哪里进」和「对不对得齐」是两个独立的问题。**

因为 `m_B = C/B_B` 且 `P_B/m_B = 60/C = T`，所以：

```
s_B 每平移整数个 P_B（整数拍），t_beat 就平移整数个 T（整数步）——相位不变。
```

**⇒ 选曲入点（跳过前奏、从副歌进）和相位对齐是两个正交的问题！**
可以先把入点定在音乐上最合适的位置，再把它吸附到最近的拍线；对相位的影响只有"整拍平移"，可以完全忽略。

### 4.5 相位对齐的公式

> **💡 大白话**：就三步 ——
> ① 算 A 的下一拍在**秒表上的第几秒**（这就是要对齐的时刻）；
> ② 挑一个 B 的音乐入点，**吸附到最近的拍线上**（由 §4.4，这一步不影响相位）；
> ③ 在①那个时刻播放②那个位置 —— **B 的第一声就是那一拍。**
> **相位由构造保证，不需要任何测量、迭代或试错。**

1. 读 A 的当前歌曲位置 `s_A`，算下一拍：

```
nextBeatSec_A = f_A + P_A · ( floor((s_A − f_A)/P_A) + 1 )
t_nextA       = now + (nextBeatSec_A − s_A) / m_A        // 落在 (now, now + T]
```

2. 选 B 的入点并吸附到拍线（4.4 保证这不影响相位）：

```
p0 = 音乐入点（0 / 副歌 / 上次播放位置）
p* = f_B + P_B · round((p0 − f_B) / P_B)
```

3. 直接**在 `t_nextA` 起播，并且就从 `p*` 起播**——B 的第一声就是那一下拍点：

```
seekTo( p* · sampleRate )
t_start = t_nextA
```

**相位由构造保证对齐，不需要任何迭代或测量。**

4. 如果想要一点"引子"（B 在目标拍点之前先响几拍），把入点整拍前移即可：

```
seekTo( (p* − k·P_B) · sampleRate )
t_start = t_nextA − k·T          // k 为整数，相位不变
```

5. 最后补偿"切歌路径的固定延迟差" `Δ_sw`：

```
t_start = t_nextA − k·T − Δ_sw
```

`Δ_sw` 是"新起播的 player 从 `play()` 到第一帧真实音频到达输出"与 A 的稳态路径之间的固定差（引擎 warmup、环形缓冲预填）。**这是个常数，必须实测一次，然后永久使用。** 用离线渲染模式 + 位置编码（扫频）就能测出来。

### 4.6 切歌时序（推荐落地顺序）

```
─── 准备阶段（提前 ≥ 600 ms 发起）───────────────────────────
 1. 目标时刻 = A 的下一拍，且距离 now ≥ 600 ms
    （若不足，顺延到再下一拍；A 的拍周期在墙钟上就是 T，所以最多多等半步）
 2. 后台：加载 B 的文件、解码、跑/读 CppDataAnalyzer（BPM、firstBeat、段落表）
 3. 新建 playerB（LiveStretchPlayer 实例）+ 新的 audioRenderer
 4. 由 4.5 算出 p* 与 t_start，对 playerB 执行 loadAudio + seekTo(p*)
    —— 此时 playerB 尚未 play()，不发出声音

─── 切换瞬间（t = t_start）────────────────────────────────
 5. 对 follower：setSong(B_B, f_B)      // 清相位历史，保留步频窗口
     紧接着   setMultiplier( C/B_B )   // ★ 瞬时快照，跳过 tau 斜坡
     （C 取 follower.cadenceBPM()；B_B 取 Analyzer 在该入点的 bpm_at_time）
 6. 在同一时刻：
      playerB.play()
      playerA 起 30~80 ms 淡出（或硬停）
      follower 的 setSpeed 输出改绑到 playerB
 7. A 的 player 与 audioRenderer 在淡出结束后释放

─── 之后 ───────────────────────────────────────────────
 8. follower 从 ADJUST 开始（setMultiplier 的效果）。
    因为相位已被构造对齐，hitRate 会立刻很高，
    不会被误触发 CHASE —— 用户听不到任何"追"的过程。
```

**第 5 步的顺序很关键：先 `setSong` 后 `setMultiplier`。**
`setSong` 会清空相位历史并把 `target_` 更新成 `C/B_B`；`setMultiplier(C/B_B)` 再把 `base_` 拉过去。反过来做，`setSong` 会重新算 `target_` 但不动 `base_`，等于白做。

### 4.7 硬切 vs 交叉淡化

| 方案 | 相位要求 | 实现成本 | 听感 |
|---|---|---|---|
| **v1：拍点硬切 + 30~80 ms 短淡入淡出** | 只在切换的那一拍对齐 | 低（还是两个 player，但不需要持续混音） | DJ 手法，拍点对齐时听感很好；短淡入淡出只为消爆音 |
| **v2：4 拍交叉淡化** | **整个重叠期**都要对齐 | 高（需要单一时钟的混音器；两个 engine 各自有独立线程和 warmup 延迟，会相对漂移） | 更顺滑，但不同调性会打架 |

**v1 已经把"相位对齐"这个问题完整地解决掉了**，建议 v1 先落地。

v2 的前提条件（同时也是当前架构的欠账）：
- 两个 `LiveStretchPlayer` 实例必须共享一个输出时钟。当前每个实例自己起线程 + `sleep_until` 排拍，两者会缓慢相对漂移；正确做法是**一个输出线程拉两个 engine**，而不是两个线程各自推。
- `napi_bridge_center.cpp` 目前是全局单例（`dataClip` / `g_ringBuffer` / `g_lastCallbackMs`），多实例是硬前提。

### 4.8 变速歌（多段落）怎么处理

```cpp
tempo::TempoFollower::setSong(bpm, firstBeatSec)   // 只有一对常量
cda::Paragraph::bpm_at_time(t)                     // 任意时刻的瞬时 BPM
```

对带速度变化的歌（慢前奏、渐快尾奏），需要**按段落重锚**。要点：

- `beatOffset` 是**瞬时量**，用当前的 `B` 和 `songSec` 计算。所以只要 `B` 是当前段落的 BPM、`firstBeatSec` 是当前段落的**节拍网格锚点**，结果就是对的。
- 换段时，网格要保持连续：新锚点 = 旧锚点 + k·P_旧（k 为整数），即"以最近一个拍点为新网格的起点"。
- **不要用 `setSong()` 来换段**——它会清空相位历史、把状态打回 ADJUST。需要一个轻量接口（例如 `setGrid(bpm, firstBeatSec)` 只更新网格、不清历史）。这是需要新增的最小 API。

### 4.9 跨歌的**八度（metrical level）一致性**——不做会出大事

`calcMultiplier = cadenceBPM / songBPM`，倍速被夹在 `[0.5, 2.0]`。

如果 A 歌被定性为 90 BPM、B 歌被定性为 180 BPM（同一首歌的两个八度层级），那么：

```
m*_A = 180/90  = 2.0     （顶在上限）
m*_B = 180/180 = 1.0
```

**切歌瞬间感知速度直接翻倍/减半。** 这是比相位失配严重得多的问题。

而且这正是 `CppDataAnalyzer` 里 k-means 归一化要解决的"两拍并一拍/一拍拆两拍"——**同一个混叠问题，出现在分析层**。

**规则：每首歌在分析完成后，一次性决定它的"节拍层级"，并且跨歌保持一致。**
判据建议：在候选层级（B/2、B、2B）里，选使 `|log2(C/B_candidate)|`（等价：倍速最接近 1.0）最小的那个；或者干脆用固定规则——`CppDataAnalyzer` 输出的段落 BPM 若落在 [150, 210] 就用它，落在 [75, 105] 就乘 2。**重点是这个决定必须存在、必须落库、必须对切歌两侧用同一把尺子。**

### 4.10 失败与降级

| 情况 | 降级策略 |
|---|---|
| B 尚未分析（没有 CSV） | 按"下一拍"正常切，但用 `m_B = m_A · B_A/B_B_粗略`；相位对齐会差，可接受（用户刚点歌，容忍度高） |
| B 的 BPM 明显异常（超出 [60, 220]） | 用 A 的感知速率反推 B 的等效 BPM：`B_B = C/m_A`，先保证速度连续，相位交给 follower 慢慢追 |
| 准备时间不足（< 600 ms） | 推迟到下一个拍点；A 的拍周期 = T，多等最多半步，用户无感 |
| 用户在切换瞬间步频突变 | 两首歌同用一个 follower，会自动一起跟上，网格仍然对齐——**这正是"单 follower 驱动两首歌"的价值** |
| seek 后引擎 warmup 行为异常 | 用离线 dump 预渲染一次，把 `Δ_sw` 做成常量表 |

### 4.11 ★ 反直觉但重要：对齐"歌曲网格"，不要对齐"脚步时刻"

**应该把 B 的拍点网格对齐到 A 的拍点网格**，而不是把 B 对齐到脚步落点。

理由：因为 3.7 那个"恒定延迟偏置"，A 的**听到的**拍点网格相对脚步本来就有一个固定残余偏移 `r`。如果 B 对齐到脚步（`off_meas = 0`），B 的网格就会比 A 的网格整体平移 `r`——**切歌瞬间用户会听到一次相位跳变，跳变幅度就是那个残余偏移（可能高达 1/4 拍）。**

反过来，对齐 A 的网格，`r` 被原样继承，**切歌前后的感知完全连续，而且标定误差自动抵消**——标定错了也听不出来，因为两边错得一样多。

**⇒ 这也意味着切歌的对拍逻辑完全不需要 `stepDelaySec`，两者可以独立调试。**

## 8. 开环模式（曲线 / 恒定 BPM）的相位对齐

> 前提：这两种模式下 `m` **不是**由 `TempoFollower` 给的，而是由"规定的目标步频 ÷ 歌曲 BPM"直接算出来的。
> 所以问题变成：**没有闭环，我还怎么保证拍点踩在脚步上？**

### 8.1 ★ 定理：开环下相位**根本不会漂**，只需要管「入口」

> **💡 大白话**：就是 §0.5.5 那条 ——
> **算倍速用的步频，和「目标脚步」的步频是同一个数，所以两个转盘永远同步。**
> 下面那一堆积分符号只是把这句话写成公式，**看结论就够了**：
> 开环模式下没有任何「持续对齐」的活儿，只有「进场时对不对得齐」这一个问题。

定义两个"累积相位"：

```
脚步相位   Φ_step(t) = ∫₀ᵗ C_target(τ)/60 dτ        （单位：步，连续实数）
音乐拍相位 Φ_beat(t) = (songSec(t) − f) / P(t)      （单位：拍）
```

而 `songSec` 的推进速率就是倍速 `d(songSec)/dt = m(t)`，于是 `dΦ_beat/dt = m(t)·B(t)/60`。
**只要倍速严格取 `m(t) = C_target(t) / B(t)`：**

```
┌──────────────────────────────────────────────────────┐
│  dΦ_beat/dt = C_target(t)/60 = dΦ_step/dt            │
│  ⇒ Φ_beat(t) − Φ_step(t) ≡ 常数，永不漂移            │
└──────────────────────────────────────────────────────┘
```

**证明只有一行，但含义很大：**

| 模式 | `m` 从哪来 | 相位差会漂吗 |
|---|---|---|
| 步频跟随 | 实测步频 `C_meas` | **会漂**，漂移率 = `2(m/m* − 1)` 单位/步 → 所以必须有 CHASE |
| 恒定 BPM | 规定常数 `C_const` | **不漂** |
| 曲线 | 规定曲线 `C_target(t)` | **不漂**（逐时刻成立，曲线怎么变都不漂） |

**⇒ 开环模式下没有任何"持续对齐"的工作要做。相位只在"入口事件"发生时（起播 / seek / 暂停恢复 / 切歌 / 换模式）才需要处理一次。**

这也顺带说明 §2.1 那个漂移公式的地位：**它是"闭环缺陷的度量"，不是"对齐的必需品"。**

### 8.2 那闭环为什么需要 CHASE？

因为 `m` 和 `m*` 之间有**残余**：

- `C_meas` 有噪声、有滞后（`windowN` 步的窗口 + `tau` 的平滑），不是瞬时真值；
- `m` 是离散更新 + 指数平滑，本身就在"追赶"；
- 步频是**被人改变的**外力，不是已知函数。

开环模式把 `C` 变成了"已知函数"，这三条残余**一起消失了**。

### 8.3 入口事件清单（开环模式要处理的全部情况）

| 入口事件 | 相位会发生什么 | 处理方式 |
|---|---|---|
| **起播** | 从任意相位开始 | 见 8.4（唯一真正需要决策的地方） |
| **曲线段与段之间（C 变化）** | **不漂**（只要 `m = C/B` 同步更新） | **什么都不用做** ★ |
| **拖动进度条 / seek** | 相位任意跳变 | 把目标位置吸附到最近的拍线（用 §10 的规范化锚点 + `firstBeatAtOrAfter()`） |
| **暂停 / 恢复** | 见 8.5 | 让"曲线时间轴"跟着暂停 |
| **切歌 / 接歌** | 见 §9 | |
| **模式切换**（跟随 ↔ 曲线） | `m` 会跳变（`C_meas/B` → `C_curve/B`） | 用 1~2 s 线性斜坡过渡，相位只漂 ≤0.3 单位 |

**模式切换的斜坡长度怎么定：** 斜坡期间相位漂移 ≈ `∫ 2(m/m* − 1)·(C/60) dt`。
若 `m` 变化 5%、斜坡 2 秒、180 步/分：平均 `|m/m* − 1| ≈ 0.025`

```
2 × 0.025 × (180/60) × 2 = 0.30 offset 单位   <   goodWin(0.50)
```

**⇒ 1~2 秒斜坡足够，不需要更长，也不该更短（更短会有可听的速度阶跃）。**

### 8.4 ★ 恒定 BPM 模式下「初始相位」从哪来（这个模式唯一真正的坑）

> **💡 大白话**：开环模式下，「脚步应该在哪」是我们**规定**的，不是**量**出来的，
> 所以起播时**没有任何东西可以对齐**。而夹角一开始落在哪儿，听感上是**五五开**：
> 落在左脚上 →「我在踩着拍子跑」（爽）；落在两步中间 →「踩不到点上」（难受）。
> **两种情况的差别只是一个选择。** 这一节解决的就是「怎么把最开始那个夹角定下来」。

开环模式下"脚步网格"是**规定出来的**，不是观测出来的，所以起播时**没有任何东西可以对齐**。三种做法：

**(a) 不管（自由相位）—— 不能当作最终方案**

音乐的拍点会落在相对脚步的某个**恒定**偏移上。它不抖、不漂，稳定得很。但听感上是**五五开**：

- 拍点落在左脚 / 右脚上 → "我在踩着拍子跑"，体验很好；
- 拍点落在两步正中间 → "节奏踩不到点上"，体验很差。

**因为 §3.6 的混叠，这两者恰好只差一个选择。恒定偏移在数学上无害，在感知上却是全部。**

**(b) 一次性观测标定（推荐）**

传感器还在（步数显示要用）。做法：

```
起播后的前 N 个脚步（N = 8~12）：
    用 §3.3 的配对公式算出每个脚步的 off_i
    r = 这 N 个 off_i 的**圆均值**（offset 是圆周量，不能算术平均）
若 |r| > 阈值（例如 0.15）：
    用 8.6 的"有界相位微调"把相位拉回 0，然后转入纯开环
```

拉回用 8.6 的方式，**不要用 seek**（seek 会有可听的内容跳跃）。

**(c) 倒数入场（最省事、最可靠）**

起播时先播 4 声提示音，第 5 声同时开始音乐和"用户的正式起跑"。
倒数本身就是相位对齐工具，**对齐误差只剩用户起跑的生理抖动（几十毫秒）**，一次到位、零算法。
我强烈推荐这个——**它把一个信号处理问题变成了一个交互设计问题。**

### 8.5 暂停复位：曲线时间轴必须跟着暂停

暂停时 `LiveStretchPlayer` 不产数据 → `inputConsumed()` 不前进 → `songSec` 冻结。
但"目标脚步相位" `Φ_step` 是**墙钟的函数**，它会继续走。恢复后相位差：

```
r_resume = ∫_pause C_target/60 dt   （180 步/分停 30 秒 → 90 步 → 90 mod 2 = 0，反而没事）
```

注意它**对 2 取模**，所以短暂停的相位误差是"巧合式"的：停 0.33 秒 ≈ 正好一步、停 0.67 秒 ≈ 正好两拍。**但停 1.2 秒就错得很明显了。**

**⇒ 产品决策：暂停时曲线时间轴也应该暂停。** 用户暂停是为了歇口气 / 系鞋带，回来应该接着刚才那一段跑，而不是发现曲线已经跑掉了。
实现上就是把曲线的自变量从"绝对墙钟"改成"累计播放时间"（累计 `paused_ == false` 的时长）。

### 8.6 有界相位微调（一个能在所有模式复用的小工具）

需求：**在不改变平均速度的前提下，把恒定相位偏移拉回 0。**
做法：给倍速叠加一个**有界、双向、临时**的偏差。

```
m(t) = (C_target(t) / B(t)) · (1 + δ(t))      δ ∈ [−δmax, +δmax]，δmax = 0.02
δ 的方向 = 把相位差 r 拉回 0 所需的方向（符号为 −sign(r)）
```

效果（180 步/分，δ = 1.5%）：

```
漂移速率 = 2δ × (C/60) = 2 × 0.015 × 3 = 0.09 offset 单位/秒
把 0.5 单位（1/4 拍）拉回 0 需要 ≈ 5.6 秒
```

1.5% 的速度偏差**在听感上基本不可辨**，而且只持续几秒。
**这既是"手动对齐微调滑条"的正确实现（§3.8 第 5 步），也是 8.4(b) 与所有入口事件后修正的通用手段。**

**要把它和"伺服"区分开：**

| | 有界微调（推荐） | 相位伺服（不建议默认开） |
|---|---|---|
| 触发 | 只在入口事件后 / 用户手动 | 持续 |
| 目标 | 一次性把 `r` 拉到 0，然后 δ 归零 | 持续把 `r` 压在 0 |
| 平均速度 | **严格 = 规定值** | 会被脚步带偏 |
| 本质 | 仍然开环 | 已经变回 follower |

**更好的定位是"护栏"**：平时完全开环、严格遵守曲线；**只在 `|r|` 接近 0.6（快要跑到反拍）时，才轻轻拉一把，且只朝 0 拉、不越过 0。**
既保持"音乐带节奏"的产品意图，又避免"拍点跑到对面去"的最坏体验。

### 8.7 开环模式的接线

```
t_sport  = 累计播放时间（暂停时冻结，见 8.5）
C_target = 曲线[t_sport]                    // 定时刷新 1~10 Hz 足够
B_now    = analyzer.bpm_at_time(songSec)    // 变速歌必须用瞬时值
m        = C_target / B_now × (1 + δ)       // δ 默认 0
player.setSpeed(m)
```

**两个必须注意的点：**

1. **变速歌必须用 `bpm_at_time(songSec)`，不能用全曲平均 BPM。**
   如果歌内 BPM 有变化而 `m` 用了常数，§8.1 的定理立刻失效，相位会漂——
   漂移率 = `2(m·B(t)/C − 1)`。
2. **曲线的时间轴是"运动时间"，不是"歌曲时间"。** 用户拖进度条不能让曲线跟着跳。

### 8.8 三种模式一张表

| | 步频跟随 | 恒定 BPM | 曲线 |
|---|---|---|---|
| `m` 来源 | 实测 `C_meas` | 规定常数 | 规定 `C_target(t)` |
| 谁是主 | 脚步 | 音乐 | 音乐 |
| 相位会漂吗 | **会** | 不会 | 不会 |
| 需要 CHASE 吗 | 需要 | 不需要 | 不需要 |
| 需要 `stepDelaySec` 吗 | **需要**（进 CHASE 的门槛） | 不需要（相位固定，标定只影响"落在左脚还是两步中间"） | 同左 |
| 起播相位怎么定 | 自动（闭环会收敛） | 8.4 的 (b) 或 (c) | 同左 |
| 传感器的作用 | **控制输入** | 只用于步数显示 + 8.4(b) 的一次性观测 | 同左 |

**⇒ 架构含义：把"速度来源"做成可插拔，把"入口相位对齐"做成共享模块。** 三种模式共用 §9 的接歌逻辑和 §10 的锚点规范化。

## 9. 接歌（交叉混音）

### 9.1 你现在的方案，和它的局限

"前一首播完的后一拍，卡上下一首的第一拍" = **硬切 + 结束点对齐**。作为 v1 是对的，但有四个限制：

1. **没有重叠**，严格说是"换歌"不是"接歌"。
2. **出点不可控。** A 是被 `LiveStretchPlayer::audioLoop` 里 `produced == 0` 自动结束的，你只能被动接受它的结束位置。冷结束（突然停）的歌根本没有可用的拍点。
3. **只有一个整数自由度**（B 的入点），A 的出点被"自然结束"钉死了。
4. 如果 A 的结尾是渐弱 / 没有鼓，对齐了也没有意义。

### 9.2 ★ 一般形式：两个整数自由度 + 一个相位约束

> **💡 大白话**：两首歌同时响的时候，**两根指针必须重合**。好消息是 ——
> **只要某一瞬间对上，就永远对上**（两首歌在秒表上的转速是一样的）。
> 所以「整段都对齐」这个要求，可以简化成**一个等式**。

真正的接歌要在**重叠窗口**里同时播放 A 和 B，所以两首歌的拍点必须在**整个窗口**里都重合。

**好消息**：两首歌的墙钟拍周期都是 `T = 60/C`（§4.2），所以**只要在某一瞬间重合，就永远重合**——约束从"整段"退化成一个等式。

```
A 的第 k 拍在墙钟上： t_A(k) = t_now + (f_A + k·P_A − s_A) / m_A
B 的第 j 拍在墙钟上： t_B(j) = t_edge + (f_B + j·P_B − s_B) / m_B
```

约束：存在一对 `(k*, j*)` 使 `t_A(k*) = t_B(j*) = t_edge`。取 `s_B = f_B + j*·P_B`（B 就**从它自己的第 j\* 拍起播**），则：

```
┌──────────────────────────────────────────────────┐
│  t_edge = t_A(k*)                                 │
│  s_B    = f_B + j*·P_B                            │
│  淡化窗口 = [t_edge, t_edge + L]                  │
└──────────────────────────────────────────────────┘
```

### 9.3 ★ 核心工具：把「怎么接」降维成一个**整数格点**

> **💡 大白话**：B 的入点往前挪整数拍 = 转盘转整数圈 = 指针位置不变。
> 所以「在 A 的第几拍开始接」和「从 B 的第几拍进来」这两个选择，**在相位上完全等价，随便挑**。
> **对齐是数学保证的；挑哪一对纯粹是音乐品味问题** —— 这正是 DJ 在做的事。

由 §4.4 的整拍不变性直接推出：

> **`s_B` 平移整数个 `P_B` ⇒ B 的墙钟网格平移整数个 `T` ⇒ 相对 A 的相位不变。**
> 同理，`t_edge` 平移整数个 `T` 也就是 A 的整数拍。

**⇒ `(k*, j*)` 构成一个二维整数格点，格点上每一个组合在相位上完全等价。**

**相位约束只负责"让它们对齐"，不负责"对齐在哪"。选哪个格点纯粹是音乐问题——这正是 DJ 在做的事。**

而且因为 `T` 是两首歌共用的单位，这个格点是**矩形**的：A 走多少拍、B 就走多少拍，一一对应。

### 9.4 出点怎么定（这才是"接歌"和"换歌"的分界线）

**核心动作：不要等 A 自然结束，要提前主动出点。**

```
     t_now              t_edge            t_edge + L        A 的自然结束
       │                   │                  │                 │
A  ────┼───────────────────┼▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓┼─────────────────┼──►
       │                   │  A 淡出（等功率）│                 │
B  ────┼───────────────────┼▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓┼─────────────────┼──►
       │                   │  B 淡入          │                 │
       │                   │                  │                 │
       │  准备期            A 第 k* 拍        重叠结束          │
       │  load/decode/      = B 第 j* 拍                       │
       │  analyze/seek      （相位由构造保证）                   │
       │                                                        │
       └────────── 必须留出的余量 ──────────────────────────────┘
          t_edge ≤ 自然结束 − L − 引擎延迟(120ms) − 缓冲余量
```

出点选择原则（按优先级）：

1. A 的最后一个乐句边界（8 / 16 小节）
2. A 的最后一个副歌之后
3. 用户手动指定的点

**工程硬约束**（因为 `audioLoop` 里 `produced == 0` 会自动 `running_ = false`）：
**出点必须早于自然结束至少 `L + 引擎延迟 + 环形缓冲余量`**，否则你会听到 A 先断掉、B 才接上。

**窗口为空时降级**：如果 `[now + 准备时间, 自然结束 − L − 余量]` 里没有可用的 `t_edge`，就退回 §4 的硬切方案。

### 9.5 结构对齐：小节与乐句（当前管线的真实短板）

现在只有 beat、**没有 downbeat**。拍对齐能做到"B 的拍落在 A 的拍上"，但**"谁是 1"是未知的**：
A 的第 1 拍可能对上 B 的第 3 拍 → 鼓组重音错位 → 听起来"节奏对、乐句散"。

#### 9.5.1 先澄清一个已核实的事实：**Essentia 没有 downbeat**

对项目里预编译的 `entry/src/main/cpp/libs/*/libessentia.so`（8.2 MB）做字符串扫描，结果：

```
downbeat / Downbeat / DownBeat   →  0 次命中
```

**Essentia 完全没有 downbeat / meter / bar 检测算法。** 它现有的节奏族是：

| 类别 | 可用算法 |
|---|---|
| 拍点 | `RhythmExtractor2013`（在用）、`BeatTrackerDegara`、`BeatTrackerMultiFeature`、`TempoTapDegara`、`TempoTapMaxAgreement` |
| 速度 | `PercivalBpmEstimator`、`BpmHistogramDescriptors`、`BpmRubato`、`LoopBpmEstimator` |
| 起音 / 新颖度 | `Onsets`、`OnsetRate`、`NoveltyCurve`、`SuperFluxNovelty`、`SuperFluxExtractor` |
| 拍上响度 | `BeatsLoudness`、`RhythmDescriptors` |
| 频带能量 | `BarkBands`、`EnergyBand` 等 |
| 和声 | `HPCP`、`ChordsDetection`、`ChordsDescriptors`、`Key` |
| **通用 HMM 解码** | **`Viterbi` ← 已确认编译进了你们的 `.so`（符号 `...RegistrarINS1_7Viterbi...`）** |

**⇒ 结论：Essentia 不给你 downbeat，但把做 downbeat 需要的零件全给了，还额外送了一个 Viterbi 解码器。**

#### 9.5.2 关键重构：接歌要的是**一致性**，不是**正确性**

用户不会单独听一首歌然后说"你的小节线错了"——**没有绝对参照，单曲播放时 downbeat 对错根本不可观测**。
它只在**接歌**时暴露：A 和 B 的小节相位不一致 → 鼓组重音错位。

而**只要你用同一套算法、同一个判据给两边都算，它们就"同样对 / 同样错"**。
两首歌的小节相位都比真值偏 k，混起来的相对关系**和两边都正确时完全一样**。

```
┌──────────────────────────────────────────────────────────┐
│  判据：跨歌一致性  >>  绝对正确性                          │
│  （这也是为什么"自研启发式"在这个场景里完全够用）           │
└──────────────────────────────────────────────────────────┘
```

还有一个极好的**降维**：既然只需要"相对"，那么接歌对外需要的全部信息就是

```
每首歌一个整数： bar_phase ∈ {0,1,2,3}     // 歌曲第一个 beat 落在小节的第几拍
```

**不需要完整的 downbeat 序列，`Paragraph` 里多存一个字段就够了。**

#### 9.5.3 三条可行路线

| 路线 | 成本 | 质量 | 说明 |
|---|---|---|---|
| **① 服务端 / 离线算好，写进 CSV** | 低 | 高 | **如果歌库是预置 / 可运营的，这条路的性价比碾压其余全部。** 设备端不需要 madmom，只需要读几行数字；madmom（Python）跑在桌面或服务器上就行了。CSV 的 `# model=` 字段本来就已经出现过 `madmom`，天然是现成的接口。**——前提待确认：是否存在"用户自己导入本地音乐、必须设备端离线分析"的硬需求？** |
| **② 自研"拍同步特征 + Viterbi"** | 中（~300 行） | 中 | 见 9.5.4。**没有 Python 依赖、不增加 `.so` 体积**，推荐作为设备端方案 |
| ③ 离线导出 madmom 的 BLSTM 权重，设备端纯 C++ 推理 | 高（数周） | 高 | madmom 的 downbeat 模型本质是**一组权重矩阵**（双向 LSTM），不是 Python 逻辑。桌面端用 `.pkl` 导出成 C 数组，设备端实现 LSTM 前向 + 多分辨率 log 滤波器组。因为分析是**全曲离线**的，双向（非因果）完全没问题。**这条路能把 Python 依赖彻底消灭、只搬数学模型**，但工程量大 |

#### 9.5.4 路线 ② 的具体做法（可直接实现）

```
1) 拍点： RhythmExtractor2013 → beats[]            （已有）

2) 每个 beat 算一组"downbeat 分数"（在 [beat−20ms, beat+80ms] 窗内取）：
     f1 = 低频(20~120Hz)能量        ← kick        （BarkBands / 直接对 PCM 低通）
     f2 = 起音新颖度峰值             ← 新事件进入  （SuperFluxNovelty / Onsets）
     f3 = 和弦变化指示               ← 和弦切换    （HPCP 帧差 + ChordsDetection）
   每首歌内 z-score 归一化，加权： w[i] = 0.3·f1 + 0.4·f2 + 0.3·f3

3) 全局约束解码（这一步才是关键，别只做 argmax）：
     状态 φ ∈ {0,1,2,3}  = 该 beat 在小节内的位置
     观测 b(i, φ) = w[i]（φ=0 时）否则 0
     转移 φ → (φ+1) mod 4 概率高（~0.97），允许跳拍但给小概率
     用 Essentia 自带的 Viterbi 解码 → 每个 beat 的小节内位置
     → 取第一个 beat 的 φ 就是 bar_phase

4) 稳健性：
     · 只在"有鼓的段落"上信任结果；安静段落沿用前一段的相位
     · 用前若干小节的多数票确定 bar_phase，避免中途翻相
     · 检测到 mid-song 翻相时，取占优的那一相
```

**为什么"特征弱一点没关系"**：这**不是猜**，是在解一个**带全局约束的最大似然问题**——
和 madmom 的 `DBNDownBeatTrackingProcessor` 是同一类方法（madmom 用 RNN 出观测概率、用 DBN 解码；这里用启发式特征出观测概率、用 Viterbi 解码）。
**观测模型弱一点，全局约束会把相位锁稳。**

#### 9.5.5 零成本兜底（连 ①②③ 都不做也能用）

1. **首拍先验**：从鼓点开始的歌，**歌曲的第一个 beat 极大概率就是小节第 1 拍**。对 B（从第 0 拍进入）来说 `bar_phase = 0` 已经是对的概率很高。
2. **低频交叉**：淡出 A 的低频、淡入 B 的低频（而不是整体音量交叉），能掩盖相当一部分小节错位——因为 kick 是听感上"小节在哪"的主要线索。
3. **节拍对齐本身已经贡献了 80% 的听感**，剩下的 20% 才是小节相位。

#### 9.5.6 有了 downbeat 之后公式怎么变

**整节公式完全不变**，只是把"整拍格子"换成"整小节格子"（周期从 `P` 变成 `4P`），`k*` / `j*` 的含义从小节内的第几拍升级成第几小节。

### 9.6 交叉淡化的架构前提（当前欠账）

**必须让两个 engine 共用一个输出时钟。** 现在每个 `LiveStretchPlayer` 自己起线程 + `sleep_until` 排拍，两者会**缓慢相对漂移**——混音窗口越长，漂得越多。

推荐改法（`TimeStretchEngine` 一行都不用动）：

```
现在：  playerA.audioLoop() ──► callbackA     （每个 player 一个线程，各排各的拍）
        playerB.audioLoop() ──► callbackB

改成：  一个 Mixer 线程
          while (running) {
              engineA.process(bufA, blockSize)   // 两个 engine 被同一个节拍拉起
              engineB.process(bufB, blockSize)
              out[i] = wA·bufA[i] + wB·bufB[i]   // 等功率权重
              writeToRenderer(out)
              sleep_until(nextWake += blockSize / sr)
          }
```

**淡化曲线与时长：**

| 淡化时长 | 推荐曲线 | 用途 |
|---|---|---|
| 30~80 ms | 线性 | 只为消爆音，避免内容重叠（§4.7 的 v1） |
| 1~2 拍 | 等功率 `(cos/sin)` | 短接歌 |
| 8~32 拍 | 等功率 + 可选高通/低通对切 | 正式 DJ 式接歌 |

### 9.7 与三种模式的关系

接歌逻辑**完全不依赖** `m` 从哪来——它只依赖"两首歌各自的 `m` 和拍网格"。所以：

| 场景 | 能用接歌吗 |
|---|---|
| 跟随模式 | ✅ A、B 都由同一个 follower 驱动；混音期间步频变了，两首歌**一起**变，仍然对齐 |
| 恒定 BPM / 曲线 | ✅ 由曲线驱动，同理 |
| **跨模式**（A 在跟随、B 在曲线） | ❌ **除非两边共用一个 `C`**。规则：**同一时刻只允许一个速度来源。** |

**⇒ 又一条"单速度来源"的必要性论据**（和 §4.2 是同一条）。

### 9.8 时序（推荐落地顺序）

```
─── 准备（t_edge 前 ≥ 1~2 秒，越长越好）──────────────────────
 1. 定出点：在 A 找到最后一个"可混音区"的乐句边界 → 得到 k*
 2. t_edge = t_A(k*)；检查 t_edge ≥ now + 准备时间，否则顺延整拍
 3. 后台：加载 / 解码 / 分析 B，得到 f_B、P_B、段落表
 4. 定入点：j* = B 的入点（跳过前奏 / 从副歌进 / 从第 0 拍）
 5. s_B = f_B + j*·P_B；playerB.loadAudio + seekTo(s_B)
    （playerB 此时不 play()，不出声）

─── 混音窗口（t_edge → t_edge + L）──────────────────────────
 6. 同一时刻：playerA 开始淡出、playerB.play() 开始淡入
    权重 wA(t)、wB(t) 由 Mixer 按等功率曲线计算
 7. 两个 engine 的倍速都仍然由**同一个**速度来源驱动

─── 结束（t_edge + L）──────────────────────────────────────
 8. 停止并释放 A 的 engine 与 audioRenderer

─── 之后 ──────────────────────────────────────────────────
 9. B 独占输出。若在跟随模式，follower 的 setSong(B_B, f_B)
    应在 t_edge 之前完成（不要等到混音结束才切）
```

**第 9 条的顺序很重要**：follower 的 `setSong` 必须在混音开始前完成，否则 B 在准备期和混音期的倍速还是按 A 的 BPM 算的。
但 `setSong` 会**清空相位历史**——如果 A 还在跟随模式下用同一个 follower，这会把 A 的相位历史也清掉。

**⇒ 需要一个"双网格"的安排**：混音期间 A 和 B 各用一套网格参数。最小改法是给 follower 加一个"网格栈"，或者在混音期间用一个轻量对象（`beatOffset` 是纯函数，参数很少，不必用完整的 `TempoFollower`）。**这是一个需要专门设计的接口点。**

## 10. `firstBeatSec` 为负怎么办

### 10.1 先说：这**通常不是 bug，是"弱起"**

最小二乘拟合 `t(n) = a·n² + b·n + c` 的截距 `c = t(0)`。当歌曲以弱起（anacrusis / pickup）开始、或者拟合区间覆盖了较长前奏时，`c` 落在 0 之前是完全正常的——它描述的是**"如果拍点网格往前延伸，第 0 拍会在哪里"**。

**节拍网格 `{ f + k·P : k ∈ ℤ }` 本来就是双向无限的。`f < 0` 只是选了一个在歌曲开始之前的拍当"第 0 拍"。**

### 10.2 哪些地方安全，哪些地方会炸

先给结论：**`TempoFollower` 对负的 `firstBeatSec` 是完全安全的。**

```cpp
// beatOffset：fmod 之后有负值回卷，天然支持负锚点
double rem = std::fmod(songSec - firstBeatSec_, period);
if (rem < 0.0) rem += period;          // ← 就是这一行救了它
```

`delayOffset()` 不消费 `firstBeatSec`；`CppDataAnalyzer::bpm_at_time()` 有 `if (n < 0) n = 0` 的钳制。**都没问题。**

**会被坑到的，是"把 `firstBeatSec` 当成一个可寻址位置"的地方：**

| 消费点 | 会不会炸 | 说明 |
|---|---|---|
| `beatOffset()` | 安全 | fmod + 负值回卷 |
| `TempoFollower` 其余部分 | 安全 | 不消费 `f` |
| `bpm_at_time()` | 安全 | 有 `n<0` 钳制 |
| **`seekTo()` / 进度条吸附** | **会炸** | `seekTo` 要求 `frameOffset >= 0`，算出负位置直接返回 false |
| **§9.2 接歌入点 `s_B = f_B + j*·P_B`** | **会炸** | `j*` 小时 `s_B` 可能是负的 |
| **循环 / A-B 段重复** | **会炸** | 同上 |
| **UI 显示"第一拍在 xx 秒"** | 显示负数是误导 | 应该显示规范化后的值 |

### 10.3 ★ 正确做法：**模 P 规范化**，千万不要 clamp

> **💡 大白话**：第一拍算出来是负数（比如 −0.12 秒），意思是「网格要是往前延伸，第 0 拍在歌曲开始之前」——
> **这在音乐上完全正常（弱起 / 前导拍），不是 bug。**
> - ✅ **正确**：把 −0.12 加上一个拍周期（0.353），得到 **0.233**。网格一模一样，只是换了个名字叫「第 0 拍」。
> - ❌ **错误**：直接写成 0。这会把**整个网格往后推 0.12 秒** —— 在 180 步/分下是 **0.72 个单位**，比整个「好」窗口还大。
> 症状是「听起来差了半拍」，但代码每一行看起来都对。**记住：取模是对的，截断是错的。**

```
┌────────────────────────────────────────────────┐
│  anchor = f − P · floor(f / P)     ∈ [0, P)    │
└────────────────────────────────────────────────┘
```

**网格 `{ f + k·P }` 与 `{ anchor + k·P }` 完全相同**（只是重新命名了"第几拍"），信息零损失，而且 `anchor ≥ 0` 永远成立。

> ⚠️ **最容易犯、也最难查的错：把负数 clamp 到 0。**
> clamp 会把**整个网格平移 `|f|`**。
> 例：170 BPM（`P = 0.353 s`）、`f = −0.12` ⇒ 网格整体平移 0.12 s。
> 换算成 offset：`0.12 × C/30`，180 步/分时 = **0.72 offset 单位**——比整个 good 窗口还大。
> 症状是"听起来差了半拍 / 踩不到点上"，但代码里每一行看起来都对。
> **clamp 是错的，取模才是对的。**

### 10.4 数据落库建议：两个值都存

| 字段 | 用途 |
|---|---|
| `anchor`（规范化后，∈ [0, P)） | **所有播放期计算都用它**（offset、seek、接歌入点） |
| `start_raw`（原始拟合截距 c，可能为负） | 段落连续性推导用（§4.8：换段时新锚点 = 旧锚点 + k·P_旧） |

顺便：`Options.multi_segment` 为 false 的单 BPM 模式只输出一个段落，`anchor` 就是全曲网格相位。

### 10.5 顺手把负数当**数据质量指标**用

| 情况 | 含义 | 处理 |
|---|---|---|
| `\|f\| < P` | 正常的弱起 / 网格相位 | 取模规范化，照常用 |
| `P ≤ \|f\| < 2P` | **可疑**：很可能是 `normalize_beats` 的 k-means 把开头的拍判成"半速"删掉了，导致拍序号索引错位 | 打 warning；回退到"用规范化后的 `beats[0]` 重锚" |
| `\|f\| ≥ 2P` | 拟合外推到离谱（病态数据 / 段落太短 / 二次回归发散） | 拒绝该段落的拟合锚点，回退到 `beats[0]` |

**这条闸门很便宜，但能挡掉一类"分析看起来成功、播放却对不齐"的疑难问题。**

### 10.6 ★ 更稳的锚点估计（顺手建议，收益比看上去大）

不要直接用回归截距当锚点。改用**全部拍点在相位圆周上的均值 / 中位数**：

```
phase_i = (norm_beats[i] − i · P)          // 每个拍点相对网格的相位残差
anchor  = circular_mean(phase_i)            // 或 median(phase_i)，再取模到 [0, P)
```

（`norm_beats` 用 `CppDataAnalyzer::normalize_beats` 输出的**归一化拍序号**，这样即使中间有拍被删过，索引仍然正确。）

**三个好处：**

1. **天然处理负值**——相位量本来就在圆周上，没有"负数"这个概念。
2. **不被拟合模型带偏**——线性 / 二次回归的截距是模型外推，圆均值是数据本身的相位。
3. **误差按 1/√N 缩小**——单拍检测误差约 ±10~30 ms，全曲几百拍平均后能到毫秒级。
   **这恰好也是 §4 里"两首歌各自 `firstBeatSec` 各有 ±30 ms 误差、导致接歌相位差 0.15~0.3 offset 单位"的正解。**

### 10.7 求拍点的"永远安全"写法

任何"求 ≥ 某位置的最小拍点"的地方，都用这个形式（结果**保证 ≥ minPos ≥ 0**）：

```
firstBeatAtOrAfter(minPos) = anchor + P · ceil((minPos − anchor) / P)
```

- §4.5 的入点吸附 `p*`：改成 `firstBeatAtOrAfter(p0 − P/2)`（等价于"最近的拍线"，但不会返回负数）
- §9.2 的 `s_B = f_B + j*·P_B`：改成 `firstBeatAtOrAfter(s_B_ideal)`，并把 `j*` 相应顺延
- 进度条吸附、循环点吸附：同理

**一条规则：网格永远用 `(anchor, P)` 表示，任何取点都经过 `firstBeatAtOrAfter`。这样负锚点在接口层就被彻底隔离了。**

## 11. 参考实现（可直接落地的代码片段）

> 本节是前面所有"机制"的落地版。代码按 **C++11、纯头文件、可移植** 写，风格对齐 `step_detector.hpp` / `TempoFollower.hpp`。

### 11.0 公共基建：拍点网格 `Grid`（全篇复用）

> **💡 大白话**：这个 `Grid` 就是「拍点网格」的统一写法：**一个小数（第一拍在第几秒）+ 一个周期**。
> 构造函数里做一次**取模**，把负锚点抹掉（§10.3）；之后所有取点都走 `firstAtOrAfter` / `nearest`，
> **保证永远不会算出负数**。§4、§9、§10 的所有坐标问题都由这一个类型解决。

§10 说过：**网格永远用 `(anchor, period)` 表示，负锚点在构造时就被消灭。** 这一个类型解决 §4 / §9 / §10 的全部坐标问题。
```cpp
// beatgrid.hpp —— 拍点 / 小节网格的统一表示
#pragma once
#include <cmath>

namespace beatgrid {

const double kPi = 3.14159265358979323846;

struct Grid {
    double anchor;   // ∈ [0, period)  —— 网格上的一个参考点（歌曲时间轴，秒）
    double period;   // 周期（歌曲秒）：拍网格 = 60/BPM；小节网格 = 4×拍周期

    Grid() : anchor(0.0), period(0.5) {}

    // ★ 关键：构造函数里就把锚点折进 [0, period)
    //    网格 {f + k·P} 与 {anchor + k·P} 完全相同，
    //    但 anchor ≥ 0 恒成立 ⇒ §10 里所有"负锚点会炸"的地方自动消失
    Grid(double a, double p) : anchor(0.0), period(p > 1e-9 ? p : 1e-9) {
        double k = std::floor(a / period);
        anchor = a - k * period;
        if (anchor < 0.0)      anchor += period;   // 浮点兜底
        if (anchor >= period)  anchor -= period;
    }

    // 若第 0 拍是小节内的第 barPhase 拍，返回对应的小节线网格（§9.5）
    static Grid bars(const Grid& beats, int barPhase, int beatsPerBar) {
        const int back = ((-barPhase) % beatsPerBar + beatsPerBar) % beatsPerBar;
        return Grid(beats.anchor + back * beats.period,
                    beats.period * (double)beatsPerBar);
    }
};

// ---- 取点：全部保证"结果 ≥ 给定位置"，因此永远 ≥ 0 ----

// 第一个 ≥ t 的格点
inline double firstAtOrAfter(const Grid& g, double t) {
    return g.anchor + g.period * std::ceil((t - g.anchor) / g.period);
}
// 第一个严格 > t 的格点（"下一拍"用这个）
inline double firstAfter(const Grid& g, double t) {
    return g.anchor + g.period * (std::floor((t - g.anchor) / g.period) + 1.0);
}
// 离 t 最近的格点
inline double nearest(const Grid& g, double t) {
    return g.anchor + g.period * std::floor((t - g.anchor) / g.period + 0.5);
}
// 第一个 ≤ t 的格点
inline double lastAtOrBefore(const Grid& g, double t) {
    return g.anchor + g.period * std::floor((t - g.anchor) / g.period);
}
// 连续格点序号（可为小数 / 负数）
inline double indexAt(const Grid& g, double t) { return (t - g.anchor) / g.period; }

// ---- 相位 ----

// 圈内相位 ∈ [0,1)
inline double phase01(const Grid& g, double t) {
    double rem = std::fmod(t - g.anchor, g.period);
    if (rem < 0.0) rem += g.period;
    return rem / g.period;
}

// 归一化偏移 ∈ [-1,1]：0 = 正中，+1 = 晚半拍，-1 = 早半拍
// ★ 与 tempo::beatOffset() 逐行等价 —— 两套坐标必须对得上，否则 §3.8 全错
inline double offset(const Grid& g, double t) {
    double rem = std::fmod(t - g.anchor, g.period);
    if (rem < 0.0) rem += g.period;
    const double half = g.period * 0.5;
    double off = (rem < half) ? (rem / half) : ((rem - g.period) / half);
    if (off >  1.0) off =  1.0;
    if (off < -1.0) off = -1.0;
    return off;
}

// ---- 单位换算（§1.3）----
//   1 个 offset 单位 = period/2 歌曲秒 = (period/2)/m 墙钟秒
inline double offsetToSongSec(const Grid& g, double off) {
    return off * g.period * 0.5;
}
inline double offsetToWallSec(const Grid& g, double off, double m) {
    return off * g.period * 0.5 / m;
}
inline double wallSecToOffset(const Grid& g, double tauWall, double m) {
    return tauWall * 2.0 * m / g.period;          // = τ·C/30（C=步频）
}

// 把墙壁偏移换算成 tempo::TempoFollower::stepDelaySec
// ★ 因为 delayOffset() 内部是 stepDelaySec * B / 30（"歌曲秒"语义），
//   要让上层参数保持"墙钟秒"语义，必须除以 m*（§1.3 的警告）
inline double wallDelayToStepDelaySec(double tauWall, double mStar) {
    return (mStar > 1e-9) ? (tauWall / mStar) : tauWall;
}

// ---- 混叠折叠（§3.6）----
// 折到 [-1, 1]
inline double fold(double d) {
    d = std::fmod(d + 1.0, 2.0);
    if (d < 0.0) d += 2.0;
    return d - 1.0;
}
// 折到 [-lim, lim]，lim ∈ (0,1]（TempoFollower 的 delayOffset 上限就是 1−hitWin）
inline double foldClamped(double d, double lim) {
    const double f = fold(d);
    if (f >  lim) return  lim;
    if (f < -lim) return -lim;
    return f;
}

} // namespace beatgrid
```

**为什么值得先写这一个文件**：§4 的切歌、§9 的接歌、§10 的负锚点，三处**共用**这些函数。而且 `offset()` 与 `tempo::beatOffset()` 逐行等价，保证"网格模块算出来的相位"和"TempoFollower 内部算出来的相位"永远一致——**这是最容易出隐性 bug 的地方。**

### 11.1 时间轴配对：`SongClock`（§3.3 的落地）

```cpp
// songclock.hpp —— 维护 墙钟 → 歌曲位置 的映射，支持用回填时间戳反查
#pragma once
#include <cmath>

namespace bpmw {

class SongClock {
public:
    SongClock() { reset(); }

    void reset() { head_ = 0; count_ = 0; }

    // 控制线程 / 传感器批次里周期性调用（建议 ≥ 20 Hz）
    //   wallSec : steady_clock 的墙钟秒
    //   songSec : player.getInputPosition() / sampleRate
    void sample(double wallSec, double songSec) {
        buf_[head_].wallSec = wallSec;
        buf_[head_].songSec = songSec;
        head_ = (head_ + 1) % kCap;
        if (count_ < kCap) ++count_;
    }

    // ★ 用 StepEvent.timestamp（回填时刻）反查当时的歌曲位置
    //    songSec(wall) ≈ 最近样点 + m·(wall − 最近样点墙钟)
    //    回看窗口只有几十毫秒，用当前倍速线性反推的误差在亚毫秒级
    bool songSecAt(double wallSec, double m, double& out) const {
        if (count_ == 0) return false;
        const Sample& s = buf_[(head_ + kCap - 1) % kCap];   // 最新样点
        out = s.songSec + m * (wallSec - s.wallSec);
        return true;
    }

    double lastWall() const {
        return count_ ? buf_[(head_ + kCap - 1) % kCap].wallSec : 0.0;
    }

private:
    struct Sample { double wallSec, songSec; };
    static const int kCap = 128;      // 128 点 @50 Hz ≈ 2.5 秒历史
    Sample buf_[kCap];
    int    head_;
    int    count_;
};

} // namespace bpmw
```

> **为什么不做插值**：±200 ms 内的线性外推，在倍速 ≤ 2.0、倍速变化率 ≤ 2%/秒 的条件下，位置误差 < 1 ms，远小于 §3.7 要求的 17~25 ms 抖动预算。**简单就够用。**

### 11.2 传感器批次接线（§3.1 / §3.9 的落地）

```cpp
// 每个播放实例一套
static steplib::StepDetector g_step;
static bpmw::SongClock        g_clock;
static tempo::TempoFollower   g_follow;
static double                 g_speed = 1.0;      // 当前倍速（受 mutex 保护）
static std::mutex             g_speedMx;
static double                 g_prevReportWall = 0.0;   // 上一次上报过的脚步时刻

enum class SpeedMode { FOLLOW, CONST_BPM, CURVE };
static SpeedMode g_mode = SpeedMode::FOLLOW;

// ---------- 脚步回调：在 g_step.update() 内部、同一线程同步执行 ----------
static void onStep(const steplib::StepEvent& e) {
    // ① 时钟倒退 / 重复上报防护（设备重连）
    if (e.timestamp <= g_prevReportWall) return;
    g_prevReportWall = e.timestamp;

    if (g_mode != SpeedMode::FOLLOW) return;   // 开环模式不喂脚步（§8）

    double m = 0.0;
    { std::lock_guard<std::mutex> lk(g_speedMx); m = g_speed; }

    // ② ★ 用回填时间戳反查歌曲位置 —— §3.3 / §3.7 的关键
    double songSec = 0.0;
    if (!g_clock.songSecAt(e.timestamp, m, songSec)) return;

    // ③ 喂跟随器：wallSec 用回填时刻，songSec 用反查值
    g_follow.addFootstep(e.timestamp, songSec);
}

// ---------- NAPI 入口：ArkTS 每 ~100 ms 送一批传感器数据进来 ----------
//   axArr/ayArr/azArr: Float32Array；n: 本批样点数
static napi_value OnSensorBatch(napi_env env, napi_callback_info info) {
    const double now  = steadyNow();                       // ★ 统一时钟
    const double rate = g_step.config().sample_rate_hz;

    // ① 先同步一次歌曲位置，让 SongClock 的新鲜度尽可能高
    double pos = 0.0, wall = 0.0;
    if (playerInputPos(&pos, &wall))                       // = getInputPosition()/sr, steadyNow()
        g_clock.sample(wall, pos);

    // ② 批次内第 i 个样点的墙钟 = now − (n−1−i)/rate
    //    这样即使 NAPI 批次有抖动，单个样点的时间戳仍然准确
    for (int i = 0; i < n; ++i) {
        const double t = now - (double)(n - 1 - i) / rate;
        g_step.update(ax[i], ay[i], az[i], t);             // 回调 onStep() 就在这里被调用
    }

    // ③ 推进跟随器时钟（★ 不需要独立控制线程，见 §3.1）
    g_follow.update(now);

    // ④ 算倍速并推给播放器
    applySpeed(now);
    return nullptr;
}

// ---------- 速度来源 + 推给播放器 ----------
static void applySpeed(double now) {
    double m = 1.0;
    if (g_mode == SpeedMode::FOLLOW) {
        m = g_follow.currentMultiplier();
    } else {
        // 开环（§8）：m = C(t)/B(t) · (1+δ)
        m = g_openLoop.speedNow(now, g_trim);
    }
    { std::lock_guard<std::mutex> lk(g_speedMx); g_speed = m; }
    playerSetSpeed(m);                                     // LiveStretchPlayer::setSpeed，线程安全
}
```

### 11.3 延迟标定的单位换算与折叠（§1.3 / §3.8 / §3.6 的落地）

```cpp
// delaycalib.hpp
#pragma once
#include "beatgrid.hpp"

namespace bpmw {

struct DelayCalib {
    double sensorTauSec;   // ① 生物力学相位：真落脚 → 检测到波峰（正 = 偏晚）
    double outputLatSec;   // ② 输出链延迟：代码产出 → 用户听到（蓝牙可达 0.3）

    DelayCalib() : sensorTauSec(0.0), outputLatSec(0.0) {}

    // 端到端延迟换算成需要的 delayOffset（offset 单位，§3.8）
    //   dOff = (τ_sensor − m*·L_out) · C / 30
    //   注意两项符号相反：检测偏晚要往后推，输出偏晚要往前推
    double offsetUnits(double cadenceSpm, double mStar) const {
        return (sensorTauSec - mStar * outputLatSec) * cadenceSpm / 30.0;
    }

    // 写进 tempo::TempoFollower::stepDelaySec（折叠 + 限幅，见 §3.6 混叠定理）
    //   hitWin 默认 0.25 ⇒ 限幅 ±(1−hitWin) = ±0.75
    double stepDelaySecFor(double cadenceSpm, double mStar, double songBPM,
                           double hitWin) const {
        const double d = offsetUnits(cadenceSpm, mStar);
        const double lim = (1.0 - hitWin > 0.0) ? (1.0 - hitWin) : 0.0;
        const double folded = beatgrid::foldClamped(d, lim);
        // stepDelaySec 的语义是"歌曲秒"（§1.3 的警告），除以 m* 换成墙钟秒
        //   再由 TempoFollower 内部 ×B/30 变回 offset 单位
        return folded * (songBPM > 1e-9 ? (30.0 / songBPM) : 0.0) / (mStar > 1e-9 ? mStar : 1.0);
    }
};

// ---- 从"用户拖动微调滑条"到参数：GUI 直接用 offset 单位，最直观 ----
//   nudge ∈ [-50, +50] 表示 ±0.50 offset 单位 = ±1/4 拍
inline double stepDelaySecFromNudge(int nudge, double songBPM, double mStar) {
    const double dOff = (double)nudge / 100.0;
    return dOff * (30.0 / songBPM) / (mStar > 1e-9 ? mStar : 1.0);
}

} // namespace bpmw
```

**自测向量**（可直接当单元测试，对应 §6 的实验 3）：

| C (步/分) | τ_sensor | L_out | m* | 期望 dOff |
|---|---|---|---|---|
| 180 | 0 | 0 | 1.5 | 0.00 |
| 180 | 0.100 | 0 | 1.5 | 0.60 |
| 180 | 0 | 0.250 | 1.5 | −1.35 → 折到 **+0.65** |
| 180 | 0 | 0.333 | 1.5 | −1.80 → 折到 **+0.20** |
| 180 | 0.100 | 0.250 | 1.5 | −0.75 → **−0.75**（贴限幅） |

> 最后一行正好是"最坏情况"：检测偏晚和蓝牙延迟几乎抵消，但残差 **0.75 单位 = 3/8 拍**，已经超出 `goodWin`。**这说明单独标定 µ 是不够的，必须给用户一个微调滑条（§3.8 第 5 步）。**

### 11.4 相位圆均值与置信度（§8.4 的落地）

`offset` 是**周长 2 的圆周量**，不能算术平均：`+0.9` 和 `-0.9` 的算术平均是 `0`，但它们的圆均值应该是 **±1**（同一个方向）。

```cpp
// circstat.hpp
#pragma once
#include <cmath>
#include "beatgrid.hpp"

namespace bpmw {

// 一组 offset 的圆均值，返回 [-1, 1]
// ★ 不要用算术平均 —— 这是个高频错误
inline double circularMeanOffset(const double* offs, int n) {
    if (n <= 0) return 0.0;
    double sx = 0.0, sy = 0.0;
    for (int i = 0; i < n; ++i) {
        const double ang = offs[i] * beatgrid::kPi;   // offset ∈[-1,1] → 角度 ∈[-π,π]
        sx += std::cos(ang);
        sy += std::sin(ang);
    }
    if (std::fabs(sx) < 1e-12 && std::fabs(sy) < 1e-12) return 0.0;
    return std::atan2(sy, sx) / beatgrid::kPi;        // 回到 [-1, 1]
}

// 合矢量长度 / n ∈ [0,1]：越大说明相位越一致
//   R > 0.9  → 脚步非常规整，可以信任圆均值
//   R < 0.5  → 相位散乱（脚步漏检 / 混入了挥手臂），别做任何标定
inline double circularConcentration(const double* offs, int n) {
    if (n <= 0) return 0.0;
    double sx = 0.0, sy = 0.0;
    for (int i = 0; i < n; ++i) {
        const double ang = offs[i] * beatgrid::kPi;
        sx += std::cos(ang);
        sy += std::sin(ang);
    }
    const double R = std::sqrt(sx * sx + sy * sy) / (double)n;
    return (R > 1.0) ? 1.0 : R;
}

} // namespace bpmw
```

**用法（§8.4(b) 的一次性标定）**

```cpp
// 起播后收集 N 个脚步的 off_i，再决定要不要拉一把
void tryOneShotAlign() {
    if (g_alignSamples.size() < 8) return;              // 至少 8 步
    std::vector<double> offs = g_alignSamples;
    const double r = bpmw::circularMeanOffset(&offs[0], (int)offs.size());
    const double R = bpmw::circularConcentration(&offs[0], (int)offs.size());

    if (R < 0.5) return;                                // 相位散乱，放弃标定
    if (std::fabs(r) < 0.15) { g_alignDone = true; return; }   // 已经够齐了

    g_trim.setTargetOffset(r);                          // 交给 §11.5 的 PhaseTrim 去拉
    g_alignDone = true;
}
```

### 11.5 有界相位微调 `PhaseTrim`（§8.6 的落地）

这是"对齐微调滑条"和"防反拍护栏"的**同一个实现**，只是 `guardOnly` 开关不同。

```cpp
// phasetrim.hpp
#pragma once
#include <cmath>

namespace bpmw {

// 给倍速叠加一个有界、双向、临时的偏差 δ：
//     m = (C/B) · (1 + δ)      δ ∈ [−δmax, +δmax]
// 效果：把恒定相位偏置拉回 0，而**平均速度基本不变**
//
// δ = 1.5% 时，180 步/分下的相位搬运速度 = 2δ·(C/60) = 0.09 offset 单位/秒
// ⇒ 拉回 1/4 拍（0.5 单位）需要 ≈ 5.6 秒，听感上完全察觉不到速度变化
class PhaseTrim {
public:
    double deltaMax   = 0.02;    // 最大速度偏差（2%）
    double deadband   = 0.08;    // |r| 小于它就不动（避免常驻微调）
    double gain       = 0.5;     // 比例增益：targetδ = −gain·r
    double slewPerSec = 0.01;    // δ 每秒最多变多少（防速度阶跃）
    bool   guardOnly  = true;    // true = 护栏模式：只在 |r| 超阈值时才介入
    double guardAt    = 0.60;    // 护栏进入阈值（offset 单位）
    double guardExit  = 0.20;    // 护栏退出阈值（迟滞，防止反复启停）

    PhaseTrim() : delta_(0.0), engaged_(false), manual_(0.0), hasTarget_(false) {}

    void reset() { delta_ = 0.0; engaged_ = false; hasTarget_ = false; manual_ = 0.0; }

    // 用户拖动微调滑条：直接指定一个恒定的 δ（正 = 加快）
    //   nudge ∈ [-50, +50] → δ ∈ [-2%, +2%]
    void setManual(int nudge) { manual_ = (double)nudge / 2500.0; hasTarget_ = true; }
    void clearManual() { manual_ = 0.0; hasTarget_ = false; }

    // 一次性标定用：给一个"要拉回的相位差"，让下一次 update 朝它拉
    void setTargetOffset(double r) { pendingR_ = r; pending_ = true; }

    // r  : 当前相位偏置（offset 单位，圆量）
    // dt : 距上次调用的墙钟秒
    // 返回应乘到 m 上的系数 (1 + δ)
    double update(double r, double dt) {
        if (dt <= 0.0) return factor();

        double target = manual_;

        if (pending_) { target = -gain * pendingR_; pending_ = false; }
        else if (!hasTarget_) {
            if (guardOnly) {
                if (!engaged_) {
                    if (std::fabs(r) > guardAt) engaged_ = true;
                } else {
                    if (std::fabs(r) < guardExit) engaged_ = false;
                }
                if (engaged_) target = -gain * r;   // 只朝 0 拉
            } else {
                if (std::fabs(r) > deadband) target = -gain * r;
            }
        }

        if (target >  deltaMax) target =  deltaMax;
        if (target < -deltaMax) target = -deltaMax;

        // δ 限速：不允许速度阶跃
        double d = target - delta_;
        const double lim = slewPerSec * dt;
        if (d >  lim) d =  lim;
        if (d < -lim) d = -lim;
        delta_ += d;
        return 1.0 + delta_;
    }

    double factor() const { return 1.0 + delta_; }
    double delta()  const { return delta_; }
    bool   engaged()const { return engaged_; }

private:
    double delta_;
    bool   engaged_;
    double manual_;
    bool   hasTarget_;
    double pendingR_ = 0.0;
    bool   pending_  = false;
};

} // namespace bpmw
```

**符号自检**：`r > 0` 表示脚步相对拍点**偏晚**（拍点来早了）⇒ 要把拍点往后推 ⇒ 减慢 ⇒ `δ < 0`。
而 `target = −gain·r`，`r>0` 时 `target<0` ✓。

**护栏 vs 伺服的差别（§8.6 的定位）**

| | `guardOnly = true`（推荐） | `guardOnly = false`（伺服） |
|---|---|---|
| 平时 | **δ 恒为 0，完全开环** | δ 一直非零 |
| 介入 | 只在 \|r\| > 0.60（快反拍了） | 只要 \|r\| > 0.08 |
| 平均速度 | **严格 = 曲线规定值** | 会被脚步带偏 |
| 本质 | 仍然是开环 | 已经变回 follower |

### 11.6 开环速度来源与暂停冻结（§8.5 / §8.7 的落地）

```cpp
// openspeed.hpp
#pragma once
#include <vector>
#include <cmath>

namespace bpmw {

// 运动时间轴：暂停时冻结（§8.5）
// 用户暂停是为了歇口气，回来应该接着刚才那段跑，而不是发现曲线已经跑掉了
class SportClock {
public:
    SportClock() : t_(0.0), lastWall_(0.0), running_(false), inited_(false) {}

    void reset() { t_ = 0.0; inited_ = false; running_ = false; }

    void setRunning(bool r, double wall) {
        if (!inited_) { lastWall_ = wall; inited_ = true; running_ = r; return; }
        if (running_) t_ += (wall - lastWall_);   // 结算上一段
        lastWall_ = wall;
        running_ = r;
    }

    // 每个控制周期调用，返回累计运动时间
    double tick(double wall) {
        if (!inited_) { lastWall_ = wall; inited_ = true; return t_; }
        if (running_) { t_ += (wall - lastWall_); }
        lastWall_ = wall;
        return t_;
    }

    double time() const { return t_; }
    bool   running() const { return running_; }

private:
    double t_, lastWall_;
    bool   running_, inited_;
};

// 目标步频曲线：关键点线性插值（时间单位 = 运动秒）
struct CadenceCurve {
    std::vector<double> t;   // 升序
    std::vector<double> c;   // 对应步频（步/分）

    double at(double ts) const {
        if (t.empty()) return 170.0;
        if (ts <= t.front()) return c.front();
        if (ts >= t.back())  return c.back();
        for (size_t i = 1; i < t.size(); ++i) {
            if (ts <= t[i]) {
                const double t0 = t[i-1], t1 = t[i];
                const double c0 = c[i-1], c1 = c[i];
                const double u = (t1 > t0) ? (ts - t0) / (t1 - t0) : 0.0;
                return c0 + (c1 - c0) * u;
            }
        }
        return c.back();
    }
};

// 开环速度来源
class OpenLoopSpeed {
public:
    bool         useCurve = false;     // false = 恒定 BPM 模式
    double       constCadence = 170.0;
    CadenceCurve curve;
    SportClock   sport;

    void setConstant(double cadence) { useCurve = false; constCadence = cadence; }
    void setCurve(const CadenceCurve& cv) { useCurve = true; curve = cv; }

    double targetCadence(double wall) {
        const double ts = sport.tick(wall);          // ★ 用运动时间，不是绝对墙钟
        return useCurve ? curve.at(ts) : constCadence;
    }

    // ★ 变速歌必须用瞬时 BPM —— 用了全曲平均，§8.1 的定理立刻失效
    //   para 由 CppDataAnalyzer 给出；bpm_at_time(t) 是 Paragraph 的成员
    template <class ParaT>
    double speedNow(double wall, double songSec, const ParaT& para, PhaseTrim& trim) {
        const double C = targetCadence(wall);
        const double B = para.bpm_at_time(songSec);
        if (!(B > 1e-6)) return 1.0;
        return (C / B) * trim.factor();
    }
};

} // namespace bpmw
```

**为什么 §8.1 的定理在这里是"免费"的**：只要 `B` 取的是 `bpm_at_time(songSec)`，
`dΦ_beat/dt = m·B/60 = C/60 = dΦ_step/dt` 就恒成立——**曲线上每个拐点都不需要任何额外处理。**
反过来，如果偷懒用全曲平均 BPM，漂移率立刻变成 `2(m·B(t)/C − 1)`，几秒就漂出窗口。

**暂停冻结的三个联动点**（少一个都会错位）：

| 联动点 | 怎么做 |
|---|---|
| `SportClock` | `setRunning(false, now)` —— 曲线时间轴冻结 |
| 音频 | `player.pause()` —— `songSec` 冻结 |
| `PhaseTrim` | `reset()` —— 清掉暂停前的 δ |
| 恢复时 | 三者同时动，**相位差为 0**，不需要任何补偿 |

### 11.7 切歌对拍 `planSwitch`（§4.5 的落地）

先把 §4 的推导收成一个可直接调用的函数。**关键是三个量都是"听到"的时间轴，不是"产出"的：**
`aLeadSec` 把 `getInputPosition()/sr` 折回"用户正在听的歌曲位置"，`bLeadSec` 把"B 起播"折回"B 的第一帧被听到"。
两者都是一次标定、永久使用的常数（§4.5 第 5 步）。

```cpp
// switchplan.hpp
#pragma once
#include <cmath>
#include "beatgrid.hpp"

namespace bpmw {

struct PlaybackCalib {
    // A（稳态播放中）：getInputPosition()/sr 领先"用户听到"的歌曲秒数
    //   ≈ (引擎固有延迟 + 输出延迟) · m_A
    double aLeadSec;
    // B（即将起播）：从 play() 到"第一个输入帧被听到"的墙钟秒数
    //   ≈ 引擎固有延迟 + 输出延迟 + 环形缓冲预填
    double bLeadSec;

    PlaybackCalib() : aLeadSec(0.12), bLeadSec(0.14) {}   // 默认值仅作占位，必须实测
};

struct SwitchPlan {
    bool      ok;
    double    tEdge;       // B 的第一拍应该"被听到"的墙钟时刻
    double    tStart;      // 调 playerB.play() 的时刻 = tEdge − lead·T − bLeadSec
    long long seekFrame;   // playerB 的 seekTo 目标
    int       leadBeats;   // 前面留了几个整拍的引子

    SwitchPlan() : ok(false), tEdge(0), tStart(0), seekFrame(0), leadBeats(0) {}
};

// 输入：
//   now          当前墙钟
//   sA           A 的歌曲位置（= getInputPosition()/sr，秒）
//   mA           A 的当前倍速
//   gA           A 的拍网格
//   aEndSec      A 的总时长（秒）
//   gB, mB       B 的拍网格与目标倍速（mB = 当前步频 / B_B）
//   bLenSec      B 的总时长（秒）
//   entryPrefSec B 的音乐入点偏好（0 / 副歌位置 / 上次播放位置）
//   wantLead    希望留几个整拍的引子
//   minLeadSec  从 now 到 tStart 至少要留的准备时间（load/decode/seek 要花的时间）
SwitchPlan planSwitch(double now,
                      double sA, double mA, const beatgrid::Grid& gA, double aEndSec,
                      const beatgrid::Grid& gB, double mB, double bLenSec,
                      double entryPrefSec, int wantLead,
                      const PlaybackCalib& cal, double minLeadSec)
{
    SwitchPlan r;
    const double T = gB.period / mB;          // 墙钟拍周期（两首歌相同，≈ 60/步频）

    // ---- 1) A 的"被听到"位置 ----
    const double sAHear = sA - cal.aLeadSec;

    // ---- 2) A 的下一拍（听到时刻）作为对齐点 ----
    double tEdge = now + (beatgrid::firstAfter(gA, sAHear) - sAHear) / mA;

    // ---- 3) B 的入点：音乐入点吸附到最近拍线（§4.4 整拍不变性 ⇒ 不影响相位）----
    double sB0 = beatgrid::nearest(gB, entryPrefSec);
    if (sB0 < 0.0)          sB0 += gB.period;
    if (sB0 >= bLenSec)     sB0  = beatgrid::lastAtOrBefore(gB, bLenSec - 1e-6);

    // ---- 4) 引子：整拍前移（相位不变），同时保证 seek 目标 ≥ 0 ----
    int lead = wantLead;
    while (lead > 0 && (sB0 - lead * gB.period) < 0.0) --lead;
    double sB     = sB0 - lead * gB.period;
    double tStart = tEdge - lead * T - cal.bLeadSec;

    // ---- 5) 准备时间不足就整体顺延整拍（相位不变）----
    while (tStart < now + minLeadSec) { tEdge += T; tStart += T; }

    // ---- 6) 边界检查 ----
    if (sB < 0.0 || sB >= bLenSec)                             return r;   // B 入点非法
    if (tEdge > now + (aEndSec - sAHear) / mA)                 return r;   // A 余量不足
    if (mB < 1e-6 || gB.period < 1e-6)                         return r;

    r.ok        = true;
    r.tEdge     = tEdge;
    r.tStart    = tStart;
    r.leadBeats = lead;
    r.seekFrame = (long long)std::llround(sB * 44100.0);       // 换成实际采样率
    return r;
}

} // namespace bpmw
```

**逐条对应 §4.5**

| §4.5 的步骤 | 代码里 |
|---|---|
| 1. 算 A 的下一拍 | 第 2 步 `firstAfter(gA, sAHear)` |
| 2. 入点吸附拍线 | 第 3 步 `nearest(gB, entryPrefSec)` |
| 3. 直接起播，第一声就是拍点 | 第 5、6 步：`tEdge` 就是相位对齐点 |
| 4. 引子（整拍前移） | 第 4 步 `sB0 − lead·P_B`、`tStart − lead·T` |
| 5. 补偿 `Δ_sw` | `bLeadSec`（并入一次标定的常数） |

**相位恒等自检**（可直接写成断言）：
`(tEdge − tStart − bLeadSec) / T` 必须是整数（就是 `lead`）——
换句话说，**B 的起播时刻相对 A 的下一拍永远差整数个 T，这是相位对齐的充分必要条件。**

### 11.8 接歌 `planMix` + Mixer（§9.2 ~ §9.6 的落地）

#### 11.8.1 §9.2 的推导可以再化简一步（重要）

> **💡 大白话**：A 和 B 的「一小节」在秒表上**一样长**（都等于你走四步的时间）。
> 所以两条小节线**要么永远重合、要么永远错开**，没有中间状态。
> **⇒ 只要 B 的起播时刻正好落在 A 的一条小节线上，之后就永远对齐。**
> 于是「什么时候接」和「从哪儿进」变成两个**互不干扰**的选择，随便配。

前面把接歌写成"两个整数自由度 + 一个相位约束"。到了小节粒度上，其实更简单：

```
A 的小节墙钟周期 = 4·P_A/m_A = 4·(60/B_A)/(C/B_A) = 240/C = 4T
B 的小节墙钟周期 = 4·P_B/m_B = 240/C = 4T      ← 完全相同！
```

**两条小节格点周期相同，所以它们要么永远重合，要么永远错开。而"永远重合"的充要条件只有一个：
B 的起播时刻落在 A 的一条小节线上。**

```
┌────────────────────────────────────────────────────────────┐
│  ⇒ t_edge 与 s_B 是两个【完全独立】的自由度：               │
│      t_edge ∈ A 的小节线格点   ← 决定"什么时候接"            │
│      s_B    ∈ B 的小节线格点   ← 决定"从哪里进"              │
│  任取一对，相位都自动对齐。剩下的纯粹是音乐性打分。          │
└────────────────────────────────────────────────────────────┘
```

（§9.2 的 `s_B = f_B + j*·P_B` 是"只允许在小节的第 0 拍进入"的特例。放开到任意小节线后，两个自由度就解耦了。）

#### 11.8.2 `planMix`

```cpp
// mixplan.hpp
#pragma once
#include <cmath>
#include "beatgrid.hpp"

namespace bpmw {

struct MixPlan {
    bool      ok;
    double    tEdge;        // 混音起点 = A 的小节线 = B 起播被听到的时刻
    double    tStartB;      // = tEdge − bLeadSec
    double    fadeLenSec;   // 交叉淡化窗长（整数个小节）
    long long seekB;        // B 的入点（小节线对齐）
    int       kBarA;        // A 的小节序号（调试 / 日志用）

    MixPlan() : ok(false), tEdge(0), tStartB(0), fadeLenSec(0), seekB(0), kBarA(0) {}
};

inline const double kEndMarginSec = 0.15;   // A 自然结束前必须留的余量（引擎延迟 + 缓冲）

// barA / barB: 由 Grid::bars(拍网格, barPhase, 4) 得到的小节线网格
// fadeBars    : 淡化窗长（小节数），常用 2 / 4 / 8
// entryPrefSec: B 的音乐入点偏好
MixPlan planMix(double now,
                double sA, double mA, const beatgrid::Grid& barA, double aEndSec,
                const beatgrid::Grid& barB, double mB, double bLenSec,
                int fadeBars, double entryPrefSec,
                const PlaybackCalib& cal, double minPrepSec)
{
    MixPlan r;
    const double barT   = barA.period / mA;         // 小节墙钟长 = 4T
    const double L      = fadeBars * barT;
    const double sAHear = sA - cal.aLeadSec;
    const double tAEnd  = now + (aEndSec - sAHear) / mA;   // A 自然结束的墙钟时刻

    // ---------- 自由度 1：A 的出点（必须是 A 的小节线） ----------
    double tEdge = now + (beatgrid::firstAfter(barA, sAHear) - sAHear) / mA;
    while (tEdge < now + minPrepSec) tEdge += barT;        // 准备时间
    if (tEdge + L + kEndMarginSec > tAEnd) return r;       // ← 窗口不够，降级硬切（§9.4）

    // ---------- 自由度 2：B 的入点（必须是 B 的小节线）★ 与 tEdge 完全独立 ----------
    double sB = beatgrid::nearest(barB, entryPrefSec);
    if (sB < 0.0) sB += barB.period;
    while (sB + L * mB > bLenSec && sB - barB.period >= 0.0) sB -= barB.period;
    if (sB + L * mB > bLenSec) return r;                   // B 内容不够

    r.ok         = true;
    r.tEdge      = tEdge;
    r.tStartB    = tEdge - cal.bLeadSec;
    r.fadeLenSec = L;
    r.seekB      = (long long)std::llround(sB * 44100.0);
    r.kBarA      = (int)std::floor(beatgrid::indexAt(barA, sAHear + mA * (tEdge - now)));
    return r;
}

} // namespace bpmw
```

**窗口为空时怎么办（§9.4 的降级）**：`planMix` 返回 `ok = false` 时，退回 §11.7 的 `planSwitch`（拍点硬切）。

#### 11.8.3 Mixer（§9.6 的落地）

现在每个 `LiveStretchPlayer` 自己起线程排拍，两个实例会**相对漂移**。改成单线程拉两个 engine：

```cpp
// mixer.cpp（伪代码级，重点是"谁驱动谁"）
// 现在：playerA.audioLoop() ─► callbackA     每实例一个线程，各排各的拍
//        playerB.audioLoop() ─► callbackB
//
// 改成：一个 Mixer 线程，同一个时钟拉两个 engine。TimeStretchEngine 一行都不用改。

// 等功率交叉淡化权重（wA² + wB² = 1）
inline void equalPower(double x, float& wA, float& wB) {
    if (x < 0.0) x = 0.0;
    if (x > 1.0) x = 1.0;
    const double a = x * 3.14159265358979323846 * 0.5;
    wA = (float)std::cos(a);
    wB = (float)std::sin(a);
}

void mixerLoop(const MixPlan& plan, int block, int ch, int sr, double speed) {
    auto nextWake = std::chrono::steady_clock::now();
    std::vector<float> bufA(block * ch, 0.0f), bufB(block * ch, 0.0f), out(block * ch);
    std::vector<float*> pA(ch), pB(ch);
    for (int c = 0; c < ch; ++c) {
        pA[c] = bufA.data() + (size_t)c * block;
        pB[c] = bufB.data() + (size_t)c * block;
    }

    bool bStarted = false;
    while (running) {
        const double now = steadyNow();

        // --- A：混音窗口结束就停 ---
        const bool aOn = (now < plan.tEdge + plan.fadeLenSec);
        if (aOn) { engineA.setSpeed(speed); engineA.process(pA.data(), block); }
        else     { std::fill(bufA.begin(), bufA.end(), 0.0f); }

        // --- B：到点起播，之后一直响 ---
        if (!bStarted && now >= plan.tStartB) { engineB.setSpeed(speed); bStarted = true; }
        if (bStarted) { engineB.setSpeed(speed); engineB.process(pB.data(), block); }

        // --- 权重 ---
        float wA = 1.0f, wB = 0.0f;
        if (bStarted) equalPower((now - plan.tEdge) / plan.fadeLenSec, wA, wB);
        else if (!aOn) { wA = 0.0f; wB = 1.0f; }

        for (int i = 0; i < block * ch; ++i) out[i] = wA * bufA[i] + wB * bufB[i];
        writeToRenderer(out.data(), block);

        nextWake += std::chrono::microseconds((long long)((double)block * 1e6 / sr));
        std::this_thread::sleep_until(nextWake);
    }
}
```

**必须同时改的三件事**（否则 Mixer 也救不了）：

1. **两个 engine 必须共享同一个 `setSpeed` 值** —— 混音期间步频一变，两首歌要**一起**变，否则网格立刻错开（§9.7）。
2. **单实例状态下沉** —— 现在的 `dataClip` / `g_ringBuffer` / `g_lastCallbackMs` 是全局单例，两个 player 会互相踩。
3. **两个 `(B, f)` 网格要并存** —— 混音期间 A 和 B 各有一套；`TempoFollower` 是单网格的，所以混音期不要用它，
   改用 `beatgrid::offset()` 这个纯函数即可（格子和倍速都由上层给）。

#### 11.9.2 每拍的 downbeat 观测分数

```cpp
// beatfeat.hpp
#pragma once
#include <vector>
#include <cmath>

namespace dbn {

const double kPi = 3.14159265358979323846;

struct OnePole {
    double a, y;
    OnePole() : a(0.0), y(0.0) {}
    void setCutoff(double fc, double fs) {
        a = 1.0 - std::exp(-2.0 * kPi * fc / (fs > 1.0 ? fs : 1.0));
    }
    inline double process(double x) { y += a * (x - y); return y; }
};

// 对每个 beat 算 downbeat 分数 w[i] ∈ [0,1]
//   x     : mono PCM（float，[-1,1]）
//   sr    : 采样率
//   beats : 拍点时间（秒，升序）
inline void beatFeatures(const std::vector<float>& x, int sr,
                         const std::vector<double>& beats,
                         std::vector<double>& w)
{
    const int N = (int)beats.size();
    w.assign(N, 0.0);
    if (N <= 0 || x.empty()) return;

    // ---- 1) 全曲一次性算两条包络（★ 不能在 beat 窗口里分段滤波，会丢掉滤波器状态）----
    std::vector<float> envLow(x.size()), envMid(x.size());
    {
        OnePole lpLow, lpMid;
        lpLow.setCutoff(120.0,  sr);     // 低频 ≈ kick
        lpMid.setCutoff(2000.0, sr);     // 中宽带 ≈ 起音
        for (size_t k = 0; k < x.size(); ++k) {
            envLow[k] = (float)std::fabs(lpLow.process(x[k]));
            envMid[k] = (float)std::fabs(lpMid.process(x[k]));
        }
    }

    // ---- 2) 每个 beat 在自己的窗内取峰 ----
    std::vector<double> f1(N, 0.0), f2(N, 0.0);
    for (int i = 0; i < N; ++i) {
        const double t = beats[i];
        const int i0 = (int)((t - 0.020) * sr);
        const int i1 = (int)((t + 0.080) * sr);
        double pkLow = 0.0, pkFlux = 0.0, prevMid = 0.0;
        for (int k = (i0 < 0 ? 0 : i0); k < i1 && k < (int)x.size(); ++k) {
            const double lo  = envLow[k];
            const double mid = envMid[k];
            if (lo > pkLow) pkLow = lo;
            const double d = mid - prevMid;          // 正半波差分 ≈ 廉价谱通量
            if (d > pkFlux) pkFlux = d;
            prevMid = mid;
        }
        f1[i] = pkLow;
        f2[i] = pkFlux;
    }

    // ---- 3) 曲内 z-score → logistic 压到 [0,1] ----
    //     用 logistic 而不是硬归一化，是为了让"离群的大值"不会把其余拍全压成 0
    for (int pass = 0; pass < 2; ++pass) {
        std::vector<double>& v = (pass == 0) ? f1 : f2;
        double mu = 0.0;
        for (int i = 0; i < N; ++i) mu += v[i];
        mu /= (double)N;
        double var = 0.0;
        for (int i = 0; i < N; ++i) { const double d = v[i] - mu; var += d * d; }
        var /= (double)N;
        const double sd = std::sqrt(var > 1e-18 ? var : 1e-18);
        for (int i = 0; i < N; ++i) {
            const double z = (v[i] - mu) / sd;
            v[i] = 1.0 / (1.0 + std::exp(-z));
        }
    }

    // ---- 4) 加权 ----
    //   kick 检测力一般（four-on-the-floor 每拍都有 kick，判别力接近 0）
    //   起音/新事件（crash、bass 进入、和弦切换）判别力更强
    const double a1 = 0.35, a2 = 0.65;
    for (int i = 0; i < N; ++i) w[i] = a1 * f1[i] + a2 * f2[i];
}

} // namespace dbn
```

**可选升级（用 Essentia 的现成件，判别力更好）**

| 特征 | Essentia 算法 | 说明 |
|---|---|---|
| f1 低频能量 | ```BarkBands``` / ```LowPass``` + ```Energy``` | 比手写一阶低通准 |
| f2 起音新颖度 | ```SuperFluxNovelty``` / ```Onsets``` | 比正半波差分准得多 |
| f3 和弦变化 | ```HPCP``` + ```ChordsDetection``` | Goto 的经典判据，**判别力最强**，但代码量也最大 |

三条特征一起用时的建议权重：`0.25 / 0.45 / 0.30`（把 `a1/a2` 扩成三项即可）。

#### 11.9.3 4 态 Viterbi（全局约束，这才是关键）

> **💡 大白话**：Viterbi 就是在「每个拍像不像小节第一拍」这一串**模糊的分数**上，
> 找一条**整体最合理**的解释（到底哪几拍是小节第一拍）。
> **为什么要整体看？** 因为音乐有个硬规矩：**小节第一拍之间必须隔 4 拍。**
> 单看某一拍可能判错，但加上这条规矩，整条线索就锁死了。
> 代码里的「转移概率」就是这条规矩的松紧程度：允许偶尔漏拍/多拍，但代价很高。

```cpp
// bardecoder.hpp
#pragma once
#include <vector>
#include <cmath>

namespace dbn {

// 每个 beat 在小节内的位置：0 = downbeat，1/2/3 = 第 2/3/4 拍
// 观测 w[i] ∈ [0,1] 来自 11.9.2
class BarDecoder {
public:
    int beatsPerBar = 4;

    // 状态转移 = "这一拍相对上一拍推进了几个小节位置"
    //   把这些"跳"的概率放开，Viterbi 才能顺便纠正检测器的漏拍/多拍
    double pAdvance1 = 0.950;   // 正常推进 1 拍
    double pAdvance2 = 0.030;   // 漏检了 1 拍
    double pAdvance3 = 0.015;   // 漏检了 2 拍
    double pAdvance0 = 0.005;   // 多报了 1 拍

    bool decode(const std::vector<double>& w,
                std::vector<int>& barPhase, double& conf) const
    {
        const int N = (int)w.size();
        const int K = beatsPerBar;
        barPhase.clear();
        conf = 0.0;
        if (N <= 0 || K < 2 || K > 8) return false;

        // ---- 对数转移表 ----
        double lt[8][8];
        for (int q = 0; q < K; ++q) {
            for (int r = 0; r < K; ++r) {
                const int adv = ((r - q) % K + K) % K;
                double p = 1e-9;
                if      (adv == 1) p = pAdvance1;
                else if (adv == 2) p = pAdvance2;
                else if (adv == 3) p = pAdvance3;
                else if (adv == 0) p = pAdvance0;
                lt[q][r] = std::log(p);
            }
        }

        // ---- 观测对数似然 ----
        //   q == 0 : P(w | downbeat)    ∝ 0.5 + 0.5·w
        //   q != 0 : P(w | 非 downbeat) ∝ 0.5 − 0.5·w/(K−1)
        auto logObs = [K, &w](int i, int q) -> double {
            double x = w[i];
            if (x < 0.0) x = 0.0;
            if (x > 1.0) x = 1.0;
            return (q == 0) ? std::log(0.5 + 0.5 * x)
                            : std::log(0.5 - 0.5 * x / (double)(K - 1));
        };

        // ---- Viterbi（对数域 max-plus）----
        std::vector<double> prev(K, 0.0), cur(K, 0.0);
        std::vector<std::vector<int> > back(N, std::vector<int>(K, 0));

        for (int q = 0; q < K; ++q)
            prev[q] = std::log(1.0 / (double)K) + logObs(0, q);   // 均匀先验

        for (int i = 1; i < N; ++i) {
            for (int r = 0; r < K; ++r) {
                double best = -1e300;
                int    arg  = 0;
                for (int q = 0; q < K; ++q) {
                    const double s = prev[q] + lt[q][r];
                    if (s > best) { best = s; arg = q; }
                }
                cur[r]      = best + logObs(i, r);
                back[i][r]  = arg;
            }
            prev.swap(cur);
        }

        // ---- 回溯 ----
        int best = 0;
        for (int q = 1; q < K; ++q) if (prev[q] > prev[best]) best = q;

        barPhase.assign(N, 0);
        int q = best;
        for (int i = N - 1; i >= 0; --i) { barPhase[i] = q; q = back[i][q]; }

        // ---- 置信度：最优 vs 次优终点的差距（每拍平均后 logistic 到 [0,1]）----
        double second = -1e300;
        for (int t = 0; t < K; ++t) if (t != best && prev[t] > second) second = prev[t];
        conf = 1.0 / (1.0 + std::exp((second - prev[best]) / (double)N));
        return true;
    }
};

} // namespace dbn
```

#### 11.9.4 组装 + 落库

```cpp
// 分析完成后，为每首歌产出一个整数（§9.5.2 的降维）
struct SongBarInfo {
    int    barPhase;       // 歌曲第一个 beat 在小节内的位置 ∈ [0,4)
    int    beatsPerBar;    // 固定 4（先不做变拍号）
    double conf;           // 置信度；< 0.6 就当没算出来，退回首拍先验（§9.5.5）
};

SongBarInfo analyzeBarPhase(const std::vector<float>& mono, int sr,
                            const std::vector<double>& beats)
{
    SongBarInfo out; out.barPhase = 0; out.beatsPerBar = 4; out.conf = 0.0;
    if (beats.size() < 16) return out;                  // 拍太少，不做判断

    std::vector<double> w;
    dbn::beatFeatures(mono, sr, beats, w);

    dbn::BarDecoder dec; dec.beatsPerBar = 4;
    std::vector<int> pos; double conf = 0.0;
    if (!dec.decode(w, pos, conf) || pos.empty()) return out;

    out.barPhase = pos[0];                              // ★ 第一个 beat 的位置
    out.conf     = conf;
    return out;
}

//   beatgrid::Grid barB = beatgrid::Grid::bars(gB, info.barPhase, info.beatsPerBar);

**为什么 `pos[0]` 就是要的东西**：`decode()` 输出的 `pos[i]` 是"第 i 个 beat 在小节内的位置"，
而 §9.5.2 定义的 `bar_phase` 正是"歌曲第一个 beat 在小节内的位置"——**一次解码，一个整数，接歌的全部需求就满足了。**

**稳健性三件套（§9.5.4 第 4 条）**

| 场景 | 对策 |
|---|---|
| 置信度低（`conf < 0.6`） | 退回首拍先验（`barPhase = 0`） |
| 安静段落（前奏、尾奏、纯人声） | 该段落的 `w` 接近 0，Viterbi 会自动沿用转移先验，不会乱翻相 |
| 中途翻相 | `pos[0]` 取的是**全局最优路径的起点**，Viterbi 的全局性天然抑制中途翻相 |

### 11.10 锚点质量闸门与圆均值估计（§10.5 / §10.6 的落地）

```cpp
// anchor.hpp
#pragma once
#include <vector>
#include <cmath>
#include "beatgrid.hpp"

namespace bpmw {

enum AnchorQuality { ANCHOR_OK, ANCHOR_SUSPECT, ANCHOR_REJECT };

// §10.5 的数据质量闸门
//   fRaw : 拟合截距（可能为负）
//   P    : 拍周期（秒）
inline AnchorQuality checkAnchor(double fRaw, double P, const char** why) {
    const double a = std::fabs(fRaw);
    if (a < P)       { if (why) *why = "ok";                       return ANCHOR_OK; }
    if (a < 2.0 * P) { if (why) *why = "|anchor| in [P,2P): 索引可能错位"; return ANCHOR_SUSPECT; }
    if (why) *why = "|anchor| >= 2P: 拟合外推发散";
    return ANCHOR_REJECT;
}

// §10.6 用"相位圆均值"重估锚点（比回归截距稳得多）
//   beatTimes : 拍点时间（秒，升序）
//   beatIndex : 对应的【归一化拍序号】（用 CppDataAnalyzer::normalize_beats 的输出）
//   P         : 拍周期（秒）
// 返回 anchor ∈ [0, P)
inline double estimateAnchorCircularMean(const std::vector<double>& beatTimes,
                                         const std::vector<int>& beatIndex,
                                         double P)
{
    if (beatTimes.empty() || beatTimes.size() != beatIndex.size() || P <= 0.0)
        return 0.0;

    double sx = 0.0, sy = 0.0;
    for (size_t i = 0; i < beatTimes.size(); ++i) {
        const double phase = beatTimes[i] - (double)beatIndex[i] * P;   // 相位残差（秒）
        const double ang   = 2.0 * beatgrid::kPi * phase / P;
        sx += std::cos(ang);
        sy += std::sin(ang);
    }
    if (std::fabs(sx) < 1e-12 && std::fabs(sy) < 1e-12) return 0.0;

    double phase = std::atan2(sy, sx) / (2.0 * beatgrid::kPi) * P;      // → [−P/2, P/2)
    phase = std::fmod(phase, P);
    if (phase < 0.0) phase += P;                                        // → [0, P)
    return phase;
}

// 把一整套分析结果规范化成播放期要用的形式
struct SongGridInfo {
    beatgrid::Grid beat;        // 拍网格（anchor 已规范化 ∈ [0,P)）
    int    barPhase;            // §11.9.4
    AnchorQuality quality;
};

inline SongGridInfo makeSongGrid(double fRaw, double bpm,
                                 const std::vector<double>& beatTimes,
                                 const std::vector<int>& beatIndex,
                                 int barPhase)
{
    SongGridInfo g;
    g.barPhase = barPhase;
    const double P = (bpm > 1e-9) ? (60.0 / bpm) : 0.5;

    const char* why = 0;
    g.quality = checkAnchor(fRaw, P, &why);

    // ★ 无论质量如何，锚点都用圆均值重算（§10.6：天然处理负值、不被拟合模型带偏）
    //   只有拍点太少时才回退到拟合截距
    double anchor = beatTimes.empty() ? 0.0
                                      : estimateAnchorCircularMean(beatTimes, beatIndex, P);
    g.beat = beatgrid::Grid(anchor, P);          // 构造函数里再做一次规范化，幂等
    return g;
}

} // namespace bpmw
```

**为什么这一节值得单独写**：§10.3 说"clamp 是错的，取模才是对的"。
在代码层面，**这个规则只需要被遵守一次——就在 `Grid` 的构造函数里。**
只要所有网格都从 `Grid` 构造、所有取点都走 `firstAtOrAfter` / `nearest`，
**"负 `firstBeatSec`" 这个问题在整条链路上就再也不会出现。**
